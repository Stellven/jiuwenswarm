# System Ontology 0.6.1 draft: field reference

Generated by `tools/so_docs.py` from the files in `ontology/`. Do not edit by hand. Where this document and the definition files disagree, the definition files win. Terms are defined in [the dictionary](dictionary.md).

## 1. How to read this

- Every description file is a YAML file with `kind` and `id` at the top. `kind` says which of the nine file kinds it is.
- `[]` in a field path means a list; the fields after it belong to each item.
- A field that is not listed here is a structural error.
- Write `UNSET` where a value is needed but no source has provided it. Write `open` where the factory may choose. Never leave a needed value blank and never guess.
- Fields whose type is a list of names (stages, states, policies, operations, mechanisms, components) are references. Each entry must be a name declared elsewhere, as the field's meaning says; they are checked.

### Writing the YAML

- Put any text that contains a colon, a comma, a `#` or a quote inside double quotes. Unquoted, YAML splits it into fields without warning.
- Identifiers such as `comp/ds4/expert-cache` need no quotes.
- A list is written `[a, b]` or one `- item` per line. A field typed as a list must be a list even with one entry.
- Several descriptions may share one file, separated by a line containing only `---`. No separator is needed before the first.
- A key written twice in the same object is an error.
- Write byte sizes with `unit_basis: decimal` or `binary`. With `binary`, `GB` means GiB.

The description of an engine has two layers. **System**: the engine as a whole. **Component**: one part with a single responsibility, written independently of the target machine. What a component occupies on a particular machine is written in the `composition` aspect of the engine spec for that target.

| File kind | What it is |
|---|---|
| `system` | System-level description: one inference engine as a whole. |
| `component` | Component-level description: one part of an engine with a single responsibility, independent of the target machine. A component that has no parts must do at least one of: own a state, run a policy, perform a model operation, implement a stage, be an end of a flow that crosses the engine's boundary, or send a plan or control flow. Otherwise it belongs inside another component. |
| `hardware` | Hardware description: the physical capabilities of one machine. |
| `model` | Model description: the computation to be run and the data it reads and writes. |
| `environment` | Environment description: what one machine actually offers at the time of a run. |
| `workload_profile` | Workload profile: data about a model or engine gathered from a workload. |
| `mechanism` | Mechanism: a way of making an engine more efficient, written as a checkable optimization hypothesis. |
| `engine_spec` | Engine spec: one engine for one model on one hardware, in nine aspects. |
| `evidence` | Evidence: a result from a measurement or simulation, tied to the build it was obtained on. |

## 2. Common types

| Type | Meaning | Values or fields |
|---|---|---|
| status | How a fact is known, from least to most reliable. assumed: taken for the sake of proceeding. simulated: computed by a model of the system. derived: computed by the author from other stated facts. proposed: a requirement put forward but not decided. reported: stated by a paper, a project's documents or its code. vendor_stated: stated officially by the maker. measured: observed by us with the conditions recorded. | `assumed`, `simulated`, `derived`, `proposed`, `reported`, `vendor_stated`, `measured` |
| resolution | Who fixes a field of an engine spec: required (the requester), open (the factory may choose), resolved (the factory has chosen). | `required`, `open`, `resolved` |
| value | A value. Written bare (number, text, true/false), or as an object that also carries unit, how it is known, where it comes from, and who fixes it. | `value`, `unit`, `unit_basis`, `status`, `resolution`, `source`, `note` |
| list value | A value that is a list, optionally with how it is known and who fixes it. | `value`, `status`, `resolution`, `source`, `note` |
| equivalence level | How an output relates to the reference output, from strictest to loosest: bit_exact, distribution_exact, numeric, approximate. | `bit_exact`, `distribution_exact`, `numeric`, `approximate` |
| equivalence | How the output relates to the reference output. Written as a bare level, as one case (level with reference and condition), or as a list of cases when the level differs by condition. |  |
| equivalence case | One equivalence level with the reference and the condition under which it holds. Several cases are listed when the level differs by condition, for example by sampling mode. | `level`, `relative_to`, `holds_when`, `note` |
| statement | One assertion about one property of one object. | `subject`, `property`, `value`, `unit`, `unit_basis`, `status`, `source`, `conditions` |
| claim | A result someone has stated, with where it was stated and under what conditions. | `text`, `status`, `source`, `conditions`, `baseline` |
| invariant | A condition that must hold at every moment whatever the engine chooses to do. | `id`, `text` |
| commit rule | What happens to a piece of state when drafted tokens are accepted or rejected. | `keep`, `advance`, `advance_by_replay`, `replay_records`, `restore`, `restore_then_append`, `set_to_snapshot`, `recompute`, `invalidate`, `unchanged` |
| allocation | How a piece of data occupies a memory pool: pinned (stays, counts fully against the limit); reclaimable_mapping (a file mapping the operating system may drop; needs backed_by); transient (staging for one computation; needs capacity); read_through (not kept in the pool, read from backed_by at each use); elastic (a guaranteed floor that may grow to a cap). Absent means pinned. | `pinned`, `reclaimable_mapping`, `transient`, `read_through`, `elastic` |
| timing | When something happens: offline (in a separate run before the engine serves), startup (once when the engine starts), per_request, per_window (once per verify window, that is each pass in which the full model checks one accepted token plus drafts), per_step (once per decode step), per_layer (once per layer within a step), background (alongside the main work), on_demand (when another component asks). | `offline`, `startup`, `per_request`, `per_window`, `per_step`, `per_layer`, `background`, `on_demand` |
| resolved_at | When a value becomes fixed: design (by the factory, before the engine is built), startup (by the engine, from the machine it finds), runtime (by a policy while running). | `design`, `startup`, `runtime` |
| budget | The upper limit of a resource a policy may occupy. A value, or a formula evaluated when the engine starts. | `derive`, `resolved_at`, `source` |
| template | The fragment of an engine spec a mechanism variant contributes. Same structure as the aspects, with names written as placeholders: $data, $operation, $fast_pool, $slow_pool, $path_slow_to_fast, $impl_fast, $impl_slow. | `execution`, `state`, `composition`, `policy`, `binding`, `delivery` |

Component-level description: one part of an engine with a single responsibility, independent of the target machine. A component that has no parts must do at least one of: own a state, run a policy, perform a model operation, implement a stage, be an end of a flow that crosses the engine's boundary, or send a plan or control flow. Otherwise it belongs inside another component.

| `ttft` | Time to first token. | `timing_start`, `timing_end`, `workload` | `timing_start`: Where timing starts: request sent, request admitted, or prefill begins; whether model load is included. `timing_end`: Where timing ends: first token produced, or first non-empty increment received. |
| `decode_rate` | Decode rate in output tokens per second. | `includes_first_token`, `workload` |  |
| `quality_score` | Output quality. | `baseline`, `taskset`, `comparison`, `threshold` | `baseline`: The reference implementation, weights, tokenizer and sampling settings. `comparison`: How outputs are compared: token-by-token identity, or a task score not below a threshold. |
| `context_length` | Context length: the longest sequence of prompt and output tokens the engine offers. A requirement. | `value`, `unit` | `value`: The engine holds attention state for this many tokens, so it is priced against the memory budget. |

## 13. Predicates a mechanism's preconditions may use

Each is evaluated by program against the given part and returns one of: holds, fails, depends (on a requirement not yet decided), unknown (information missing).

| Predicate | Meaning | Arguments |
|---|---|---|
| `sparse_selection` | The model has a selection operation that picks at most max_pick_ratio of the instances it chooses among. | `max_pick_ratio` |
| `selected_data_partitioned` | The weights read by the selected operation can be stored and loaded separately per selected object. |  |
| `selected_data_exceeds_direct_pool` | Those weights are larger than the limit of a memory pool a compute unit uses directly. The limit is the budget if one is set, else the allocatable capacity, else the nominal capacity. |  |
| `slower_pool_can_hold` | Another memory pool is large enough to hold all of those weights and has a path to the fast pool or can be read directly by a compute unit. |  |
| `units_with_distinct_direct_pools` | At least two compute units directly use different memory pools. |  |
| `measured_property` | The given part holds a measured statement or workload profile for the property named in args. | `property` |

## 15. Deliberately left loose

- `properties` on hardware items and `software` on an environment are free name and value pairs; no property names are fixed.
- `measured_under` and `results` on evidence are free objects.
- The fields of a requirement beyond the common ones are decided by the quantity table above, not listed in the structure.
- `interface` has only basic fields. Request lifecycle, concurrency, scheduling and fairness are not defined.
- A policy's `trigger` and an action's `steps` are text the program does not interpret.
- `calls` on a component are described in words; no machine-checkable signature is defined.
