# Independent checks of the draft node types: summary

- Of 105 parts in 3 engines the types were not drawn from, 30% fit a type cleanly, 55% partly, 15% not at all.
- A second reader assigned 100% of 62 known components to the same type as the draft.
- Of 295 removed decisions that are real design choices, the types' `choices` plainly cover 35%; 48% are not covered.
- Working from the types alone, a reader selected 17 of the 18 types of the earlier Muse design; for 7 of 43 choices the type gave no guidance.

Generated by `tools/so_nodetypes_validate.py` from the result files in this directory. Each check was done by a reader who had not seen the assignments made when the types were drafted.

## 2. Would another reader make the same assignments?

62 components of the two engines the types were drawn from, classified again from the definitions alone.

| Outcome | Count | Share |
|---|---|---|
| Same type as the draft | 62 | 100% |
| Draft's type was the reader's second choice | 0 | 0% |
| Different | 0 | 0% |

The reader's own confidence: 48 high, 11 medium, 3 low.

Because component names resemble type names, the test was repeated with names and origins hidden and only the one-sentence responsibility given (62 items, scored against a key kept outside this directory: all 62 matched the draft). Confidence 49 high, 10 medium, 3 low.

This shows the definitions are clear for the two engines they were drawn from. It says nothing about other engines; Section 1 does.

- Hard to tell apart: request-front, engine-control. both pass tokens back and drive a request; components that run a request through generations and build response events straddle the line
- Hard to tell apart: engine-control, multi-request-scheduler. engine-control keeps a live record and starts generations; once batch slots exist, the command loop also shares the engine between requests
- Hard to tell apart: conversation-reuse, attention-state-store. truncation, snapshots of the current conversation and explicit session save/load are state management that both definitions partly cover
- Hard to tell apart: decode-loop, layer-compute. a loop that launches layers in order and interleaves expert work is both 'taking tokens through every layer' and 'computing the layer'; recorded graphs are a choice of both
- Hard to tell apart: expert-transfer, expert-source. a reader that copies expert bytes from storage into a cache buffer both makes experts obtainable from the slow place and moves them into fast memory
- Hard to tell apart: layer-compute, expert-dispatch. layer-compute includes expert selection, while expert-dispatch consumes 'routing'; a router could be read as the start of dispatch
- Hard to tell apart: memory-planner, configuration. startup decisions from machine memory readings fit 'machine facts into settings' as well as budget division
- Hard to tell apart: weight-loader, expert-source. weight-loader outputs expert_layout, but a component whose only job is the expert layout table belongs equally to the expert store

| `prompt-reader` | 8 | 6 | overlap of expert reads with computation; how it yields to concurrent decoding; split of missed experts between devices while reading the prompt |
| `draft-policy` | 12 | 9 | rule for choosing among draft sources; when drafting pauses and resumes; how often the policy re-decides |

- The choices name what to size or place but rarely what happens when it cannot be had: fallbacks, retries, degradation order and refusal conditions are mostly missing.

- Nearly every type omits overlap and ordering of work in time (fetch during compute, prefill yielding to decode, side reads during a step), which is where much engine design lives.

- Stopping, pausing and threshold rules (draft confidence floors, drafting pauses, split thresholds, warm-up conditions) are absent from the speculation and dispatch types.

- State upkeep across rollback and reuse is thin: how rejected positions are undone, when checkpoints are cut and what key makes stored state reusable are not choices.

- Precedence between operator values, presets, calibration and automatic fits, and whether an operator value is a hard limit or a target, recurs in several components but has no home.

- Some decisions are model-defined facts (layer compression schedule, n-gram hash, draft token subset) rather than engine choices; the types have no place for model facts the engine must honour, nor for decisions that change output such as residency-biased routing.

## 4. Can a reader work from the node types alone?

A reader given only the node types, the Muse model and the DGX Spark descriptions selected the node types the engine needs. Compared with the Muse design derived earlier from Strata:

| | Count | Node types |
|---|---|---|
| Both select it | 17 | attention-state-store, cache-policy, configuration, decode-loop, engine-control, expert-cache, expert-dispatch, expert-source, expert-transfer, layer-compute, memory-planner, model-preparation, prompt-reader, request-front, sampler, telemetry, weight-loader |
| Only the reader | 0 |  |
| Only the earlier design | 0 |  |
| Reader could not tell | 5 | conversation-reuse, draft-policy, draft-verifier, drafter, table-reader |

Of 43 choices the reader had to settle: 15 could be settled from the inputs, 13 need a measurement, 8 need a requirement, and for **7** the node type gave nothing to reason with.

What the engine needs that no node type provides:

- A cost model or feasibility check for decoding speed: Weights are about 5 times the budget. Worst case one token needs 62 x 8 x 25.2 MB = 12.5 GB of reads, about 2.6 s at 4.8 GB/s, and with about 15 percent of experts cached the hit rate decides speed. No node type estimates tokens per second from hit rate, SSD bandwidth and compute, and memory-planner refuses start only when memory does not fit, never when speed is unacceptable.
- Layer-major expert streaming for prompt reading: A chunk of many tokens selects most experts of every layer, so reading a long prompt means streaming close to the full 399.5 GB per pass (about 83 s at 4.8 GB/s). prompt-reader assumes the same expert path as decode and has no way to read each layer's experts once and apply them to all tokens of the chunk, nor to bound how often the full set is streamed for a one-million-token prompt.
- Attention state beyond memory for long context: At the stated worst case 2.0 MB per token, 32,768 tokens already take 65 GB of the 80 GB budget and one million tokens about 2 TB. attention-state-store names 'whether old state may leave fast memory' but no node types store state on SSD, page it back, or price it; nothing chooses the offered context length.
- Storage budget planning: Storage holds the checkpoint and the prepared files. A BF16 checkpoint is about 1.63 TB (816B x 2 bytes) against 2,014.6 GB reported, so it and its prepared copy cannot both fit; even NVFP4 needs about 408 GB twice. memory-planner covers memory only.
- Mapping of resource tiers to the machine: Node types use fast_memory, slow_memory and storage; the machine has one unified pool shared by CPU and GPU plus an SSD. No rule says what slow_memory means here, so expert-source and expert-transfer collapse into one step and the split is unclear.
- Image, video and audio input (out of scope under the text-only assumption): The model has a perception_encoder with its own encoder_weights; no node type covers media decoding, the encoder, or merging encoder output into the token stream, and request-front only turns messages into tokens. Its weights would also need pricing in memory-planner.
- A source for the tokenizer, chat template and reference outputs: request-front and layer-compute both define correctness against a reference, but no node type obtains or checks the reference tokenizer, template or reference implementation, and the model file names none.

What the reader lacked in a description:

| Node type | Lacking |
|---|---|
| `expert-cache` | What fast memory means on a unified-memory machine (here the cache and the slow place are the same pool). |
| `expert-cache` | How the size is derived: a formula from budget minus priced items, and a minimum useful size (e.g. at least one layer's 8 experts). |
| `cache-policy` | What it minimises (misses per token, bytes read per token) and which usage statistics it needs as input. |
| `cache-policy` | How its fetches share bandwidth with on-demand miss fetches from the same SSD. |
| `expert-transfer` | Whether it merges with expert-source when the slow place is storage and the destination is the same pool. |
| `expert-transfer` | What fetch-ahead is predicted from and how wrong predictions are charged. |
| `prompt-reader` | How expert access is organised during a chunk, given a chunk touches most experts of each layer. |
| `prompt-reader` | How chunk size relates to expert bytes streamed per chunk and to activation memory. |
| `attention-state-store` | The model facts needed to price per-token state (number of key/value heads, head size, attention kind) and where the offered context length is decided. |
| `attention-state-store` | Which tier holds state that leaves fast memory, and how it is read back. |
| `memory-planner` | A required list of priced items with how each is sized, including attention state as a function of context length. |
| `layer-compute` | A list of model facts the builder must have (attention form, norms, activation, positional encoding, tied head) before kernels can be chosen. |
| `layer-compute` | Which device numeric formats must be confirmed before choosing kernels. |
| `table-reader` | A threshold for when a table counts (e.g. table size against the memory budget), so an ordinary embedding table can be ruled in or out. |
| `drafter` | How to judge benefit when checking a window enlarges the set of experts to fetch per layer. |
| `conversation-reuse` | Whether continuing the next turn of the live conversation is this node's job or the attention-state-store's. |
| `request-front` | Where the reference tokenizer and chat template come from. |

The reader's overall judgement: A builder could start: the selection step worked for 19 of 24 types from the given facts, and the inputs, outputs and invariants make the data flow between parts clear. The strongest part is the expert-store family, whose split into source, cache, policy, dispatch and transfer matches the central problem of this case (weights about five times the budget) and whose invariants are precise. The weakest part is that choices carry no decision criteria or cost relations, so 20 of 43 choices could not be settled from the inputs and nothing tells whether the engine will be usably fast; the three-tier memory vocabulary does not fit a unified-memory machine. Long context, prompt reading under expert streaming and storage capacity are not covered by any type.

## 5. Definitions flagged as unclear, by how many readers

| Node type | Flagged by | Problems |
|---|---|---|
| `multi-request-scheduler` | 4 | (hyperqwen) Defined as admission only, with no per-step output to the loop, yet it decides each step's composition and preemption. Its invariant (output independent of co-scheduled requests) is false here, and its effect_on_output field already concedes it. / (ninfer) Lumps sharing among requests with spanning machines; model partitioning across ranks is a different job. Pause, resume and admission permits are not mentioned. / (splash) Invariant 'output does not depend on other conversations' is contradicted by batch-width-dependent kernel splits; should be stated as intended or with a tolerance, as its effect_on_output already hints. / (reclassification) conflates sharing among requests with an engine spanning machines; expert/tensor parallelism across two machines processing the same token has no clear home |
| `conversation-reuse` | 4 | (hyperqwen) Framed as parking earlier conversations; here it is block-hash sharing among any requests, with reuse only at aligned boundaries. The equality invariant is false for this engine (greedy differs on hit vs miss). / (ninfer) Invariant of exact equality is stronger than any engine with chunked prefill can claim; it should name its reference. The truncate port does not fit restore-from-checkpoint. / (splash) Invariant of equal output fails under lower-precision stored state; and summary assumes per-conversation parking while Splash has a cross-request block cache plus an SSD tier. / (reclassification) says 'earlier conversations' but components also keep checkpoints within the current conversation and save/load sessions to files on command; scope unclear |
| `model-preparation` | 3 | (hyperqwen) The not-clause and invariant say no weight value changes, while choices allow changing precision. In this engine the main preparation work is lossy (requantization, vocabulary truncation, calibration), so the type contradicts itself on its most common use. / (ninfer) The not-clause (changes no weight value) and invariant contradict the choice 'whether precision is changed here'; in NInfer quantization is the main job of preparation. / (splash) Assumes conversion produces files on disk. Splash converts at load into memory and keeps no prepared copy, so the same job lands in weight-loader; the boundary should be the job (format conversion), not the time it runs. |
| `decode-loop` | 3 | (hyperqwen) Summary and invariant assume expert routing and a single sequence. Under continuous batching one step serves many requests and mixes prefill and decode, so decode-loop and prompt-reader cannot be told apart as units. / (ninfer) Summary assumes a per-layer handoff to the expert store; dense models and graph-replayed all-resident steps have none. Batched decode of several sequences is not mentioned. / (reclassification) recorded-graph lifecycle (record, keep, free, re-record under memory pressure) is only a choice here; no type owns it |
| `engine-control` | 3 | (hyperqwen) Summary (one request at a time) and invariant (at most one prompt read at a time) only hold for a single-stream engine. In a batching engine its per-request duties belong to the scheduler, leaving only the process loop. / (ninfer) Summary and invariant assume one request at a time and one prompt read at a time; in a batched engine control and multi-request scheduling are one component, so engine-control and multi-request-scheduler cannot be told apart. / (splash) 'One request at a time' and 'at most one prompt read at a time' are only true of single-stream engines; with a scheduler, engine-control's role is unclear versus multi-request-scheduler. |
| `attention-state-store` | 3 | (hyperqwen) Per-position state with truncation to a position does not fit recurrent (GDN) state, which is fixed-size and can be rolled back only via stored snapshots. It also does not describe a pool shared by several state kinds and requests with page ownership transfer. / (ninfer) Assumes per-position state that can be cut back to any position. Recurrent (GDN) state exists only at the frontier or checkpoints, and the store is shared across sequences with references and copy-on-write. / (splash) Summary assumes per-position state truncatable to any position. Hybrid models also have fixed-size recurrent state (GDN) that is snapshot/restore-only and committed lazily; also draft-model state and auxiliary state (indexer keys, PLE history). |
| `weight-loader` | 3 | (ninfer) The not-clause gives expert loading to the expert store, but when all experts are resident, or held in host RAM, the loader loads them. Per-rank slicing has no place. / (splash) Ports are all 'startup'. Splash re-runs loading at run time after idle release; the type has no notion of rebuildable residency. / (reclassification) bundles file opening/validation, placement and expert-layout production; a pure file reader with the architecture guard does not place weights |
| `prompt-reader` | 2 | (hyperqwen) Assumes prompt reading is a separate phase per request. Here it is chunked and interleaved in the same step as other requests' decode; the routing port does not apply to a dense model. / (ninfer) Invariant takes token-by-token reading as the reference; NInfer's reference for chunked state is its own math precision, and different chunkings may differ. |
| `draft-policy` | 2 | (hyperqwen) Invariant (changes how much work, never which tokens are accepted) is false under floating point: block length changes rounding and greedy text. Port model is per-request; here the decision is batch-wide and limited to sizes with captured graphs. / (splash) Defined as whether/which source/how many to draft. Splash's policy decides how many drafted rows to verify; and the claim effect_on_output none fails when the policy reads wall clock in an MoE model. |
| `sampler` | 2 | (hyperqwen) Separating sampler and draft-verifier assumes acceptance follows sampling; in a rejection sampler they are one computation reading both target and draft distributions. / (splash) Sampler and draft-verifier are the same GPU kernel in Splash; the separation is logical only. Also lacks a constraint-mask input. |
| `expert-dispatch` | 2 | (ninfer) effect_on_output says none unless omitting, but splitting a layer between CPU and GPU changes rounding and depends on which experts are ready at that moment. / (splash) Hard to tell from expert-transfer when there is a single path (always fetch into slot then compute); in Splash both are one host-step mechanism. |
| `memory-planner` | 1 | (hyperqwen) Its outputs target an expert cache; for a dense model the residual goes to the state pool. It omits graph memory, activation peak and drafter weights, and assumes planning is arithmetic when this engine measures by a profile run. |
| `drafter` | 1 | (hyperqwen) The only input is target activations; a lookup drafter reads token history. Proposal distribution q, on which verifier correctness depends, is not a port. A separate draft model needs its own weights and state, not listed. |
| `layer-compute` | 1 | (hyperqwen) effect_on_output says this is the model's reference arithmetic, but kernel choices here (int8 activations, int8-QK attention) are deliberate approximations; there is no way to mark a kernel variant as lossy. |
| `cache-policy` | 1 | (ninfer) Summary assumes contents follow run-time usage. NInfer chooses contents at startup from an offline table, and changes the region at run time by workload size; neither is described. |
| `draft-verifier` | 1 | (ninfer) Merges acceptance (a sampling rule) and state commit (a multi-store transaction). The checked port carries tokens, but stochastic acceptance needs distributions p and q. |
| `secondary-executor` | 1 | (splash) Tied to experts and to separate memories. Splash's second device (ANE) computes a channel share of a dense FFN on unified memory with its own precision; applies_when misses it. |
| `table-reader` | 1 | (reclassification) does not mention background prewarming of the table into the page cache; unclear whether a prewarm helper is part of it |
| `configuration` | 1 | (reclassification) unclear whether on-machine speed measurement/tuning and launch-time argument resolution belong here or are separate operations nodes |
| `request-front` | 1 | (reclassification) admission bound and client-disconnect cancellation are not mentioned; overlaps with multi-request-scheduler admission |
