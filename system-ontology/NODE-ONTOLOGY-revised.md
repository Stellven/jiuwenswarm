# Node ontology: revised version (draft 0.9)

Generated by `tools/so_nodetypes.py doc` from `ontology/node-types.draft.yaml`.

Based on the feedback that the node ontology had too much detail, I went through it again. Each node described one component of Strata down to its parameter values, call interfaces and source lines. That is knowledge about one engine, and the next engine cannot reuse it. In this draft a node is a node type: a kind of engine part that says what the part is for, what it takes and gives, what it must keep true, and how far it can change the output. I drew the types from six engines instead of one, so they are not Strata's parts under new names. Strata is the worked example: each of its parts names its type and says how Strata settles the few choices the type leaves open. Everything that is specific to one engine stays in that engine's own description.

## 1. What changed

Three versions are named in this document.

- **The reviewed version**: the node level you reviewed, one description per component of Strata.
- **The full-detail draft**: a first draft of generic node types, not sent. It has the same 44 types as now and much more written about each.
- **This draft** (0.9): the full-detail draft with the detail removed. The stored records and some sentences below call it the thin draft.

| | The reviewed version | This draft |
|---|---|---|
| What is described | each component of one engine | a kind of component, for any engine |
| How many | 43 components for Strata alone | 44 node types in 10 groups |
| Size of one description | about 5,705 characters (median) | about 848 characters (median) |
| Strata's node level in all | about 239 thousand characters | about 30 thousand characters for Strata's 43 nodes, plus about 39 thousand for the 44 types, which all engines share |
| Parameter values, call interfaces, source lines | in the node description | not in a node type. Nothing was deleted: they remain in the full description of the engine, which each node points to |
| Drawn from | Strata | 6 engines |

## 2. What a node type contains

**What I borrowed from the CC declaration.** A Capability Capsule (CC) declaration in this repository (`docs/architecture/design-package/reference/declaration.md`) describes a unit by what it promises, not by how it is built. I took that as the reference for how deep a node type should go: it answers the same kind of questions about an engine part. A node type is not a CC. It is an input that CCs read, and its format and field names are the ontology's own.

| Node type field | The question it answers |
|---|---|
| `id`, `group`, `summary`, `not` | What is its one job, and what is easily mistaken for it? |
| `needed_when` | Which property of the model, the machine or the service makes this node necessary? Absent when the job has to be done in every engine. |
| `forms` | In which distinct ways do engines realise it? |
| `takes`, `gives` | What does it consume and produce? Which node it connects to differs between engines and is stated at system level, the description of one engine as a whole. |
| `owns_state` | What does it alone keep consistent? |
| `rules` | What must it guarantee? `must`: Kept by every engine examined, within `rule_scope`. `should`: A correctness rule that some engines examined relax. An engine that relaxes it says so. `rule_scope`: Rules bind every mode whose output is meant to be used. A mode that is turned on explicitly for measurement or debugging, and whose output the engine declares not valid, is outside them; such a mode is off by default and visible in the run's settings. Draft 0.9 itself was not checked against the engines for its rules or its effect on output; the last such check, of draft 0.8 on llama.cpp, found 6 claims the engine contradicts. |
| `effect_on_output` | How far can its own work change the returned output? One or more of the five levels below. Several levels mean that which one applies depends on how an engine builds the node and on its settings. |
| `indirect_effect` | Does it also change the output through other nodes, by deciding something their effect depends on, such as how wide a step is or what is kept in memory? Present and `true` when it does. |
| `choices` | What is left for whoever builds the engine to decide? Names only, no values. Listed only when at least 2 of the 6 engines decide it; `engines` says how many. |
| `seen_in` | Which of the engines examined have a part of this type? |

The levels of `effect_on_output`. The first four are the equivalence levels the format already uses, so a node type can be compared with what a target allows to change.

| Level | Meaning |
|---|---|
| `bit_exact` | The same tokens, bit for bit. |
| `numeric` | Logits differ in their last bits. A greedy token can occasionally flip and a sampled draw can differ; quality is not expected to change. |
| `distribution_exact` | Under sampling, the same distribution but a different draw for the same seed. |
| `approximate` | A deliberate change to the computation or to stored precision. Quality can change. It is asked for, or it is a default of the engine that can be turned off. |
| `defines` | The node decides what the input or the returned output is, by design: the template, the sampling settings, a constraint, where output stops. |

Not in a node type: parameter values, call interfaces, source file and line references, measured costs, test status, and choices only one engine makes. These are facts about one engine and stay in its description.

In all: 44 node types, 55 rules, 79 choices.

## 3. The node types

Two columns need a word. **Needed when**: `always` means the job has to be done in every engine; otherwise the condition is given. **Seen in**: the number of the six engines in which I listed a part of this type. The two can differ. An engine can do an `always` job inside a part that is mainly of another type, and a conditional type is seen in all six when all six meet its condition.

### Preparation (`preparation`)

What is done before the engine starts serving: converting the model's files and measuring what later choices rest on.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `model-conversion` | Offline, obtain, pin and record the published model and produce the files this engine reads: weights in the engine's layout and precision where conversion is offline, and any derived pieces such as a reduced draft head or a corrected chat template. | The engine does not read the published files as they are, or it needs pieces derived from them. | 5 of 6 |
| `calibration` | Measure the model or the machine offline, at startup, or during an opt-in profiling run, and record results that other nodes take as fixed input. | always | 6 of 6 |

### Startup (`startup`)

Loading the model and dividing the machine's resources before the first request.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `model-loading` | At startup, and again whenever released weights are restored, open the model's files, check they are something this engine can run, and make the weights every token uses readable by the computation. | always | 6 of 6 |
| `memory-planning` | At startup, divide the memory budget among resident weights, per-sequence state, working space, reserves and caches, and refuse to start when the minimum does not fit. | always | 6 of 6 |
| `graph-capture` | Prepare the computation for fast repeated execution: compile kernels, warm up, and record execution graphs for the step shapes the engine will run. | The device benefits from pre-recorded or pre-compiled work, or first-use compilation would stall a request. | 5 of 6 |

### Computation (`computation`)

Carrying out the model's arithmetic on the machine's devices.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `layer-compute` | Compute what the model defines: embedding, attention of every kind the model has, recurrent layers, feed-forward blocks, expert selection and the selected experts, and the projection to the vocabulary. | always | 6 of 6 |
| `device-backend` | Drive a device for a step's work: submit it, report results and retirement in order, and choose the kernel variant for the device and step shape where the computation does not. | always | 4 of 6 |
| `secondary-compute` | Compute a share of a layer's work on a second device, from weights it can read where they lie or that are prepared for it ahead of the layer. | A second device can compute something sooner than moving its inputs to the main device, or has spare capacity the main device lacks. | 4 of 6 |
| `model-edit` | Apply a deliberate, optional change to the model's computation at run time, such as adding or removing a direction in its activations. | The engine offers run-time changes to the model's behaviour. | 2 of 6 (ds4, llama.cpp) |
| `step-execution` | Carry one planned step through the model: a decode step, a verify block or a prompt chunk, for one sequence or for several sharing the step. | always | 5 of 6 |
| `prompt-reading` | Read a prompt in chunks, faster than token by token, and leave behind the state generation continues from. | The engine reads prompts by a path of its own. Engines that put prompt chunks and decode rows in the same step have no separate node. | 4 of 6 |
| `media-preparation` | Fetch, decode and prepare input that is not text (images, video, documents) into the form the model's encoder takes. | The engine serves input other than text. | 4 of 6 |
| `modality-encoding` | Run the model's encoder for input that is not text and produce the embeddings the model takes in its place. | The model accepts input other than text and the engine serves it. | 5 of 6 |

### Selectively used weights (`selective-weights`)

For models that use only some of their weights per token (experts, lookup rows): keeping the right ones within reach.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `expert-source` | Keep every selectively used weight obtainable for the whole run from the slow place where all of them are held. | The model selects a few of many weight blocks per token, and they do not all sit in the memory the computation reads. | 2 of 6 (Strata, NInfer) |
| `expert-cache` | Hold as many selectively used weights in fast memory as its budget allows, and answer for any of them whether it is there and where. | Not all selectively used weights fit in fast memory, or a copy in fast memory is faster to compute from. | 5 of 6 |
| `residency-policy` | Decide which selectively used weights, or other blocks read back from slower storage into a bounded fast cache, are kept in fast memory: at startup from a ranking, or while running from use or from the size of the coming work. | There is a cache of selectively used weights. | 5 of 6 |
| `expert-fetch` | Bring absent selectively used weights into fast memory, in an order the computation that follows can rely on. | There is a cache of selectively used weights. | 5 of 6 |
| `expert-dispatch` | For each layer of each step, decide how every selected block gets computed: from fast memory, after a fetch, by another device, or not at all. | Selected blocks can be in more than one place or computed by more than one device. | 4 of 6 |
| `row-source` | Serve the rows of a large table that each token needs, without holding the whole table in fast memory. | The model has a table too large to hold whole in fast memory, of which each token reads a few rows. | 5 of 6 |
| `storage-reader` | Run the engine's reads from storage for every node that needs them, so that reads the current step depends on go ahead of reads made ahead of need. | Several kinds of data are read from the same storage while the engine runs. | 1 of 6 (Splash) |

### Sequence state (`sequence-state`)

What the engine remembers per sequence, where it is kept, and how it is reused.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `positional-state-store` | Hold the state a model keeps per position (attention keys and values, and any compressed or indexed form of them), in the format chosen for storage. This covers the served model and any secondary model, such as a draft model, that keeps state per position. | always | 6 of 6 |
| `recurrent-state-store` | Hold state that is fixed in size and overwritten as the sequence advances, with what is needed to go back: snapshots, a second copy, one slot per proposed position, or a commit deferred until acceptance is known. | The model has state that cannot be cut back to an earlier position, such as recurrent or convolution state. | 6 of 6 |
| `state-pool` | Own the memory that sequences' state shares: lay it out in pages, hand pages out and take them back, track who owns each, compact, and let shared pages be read by several sequences. | Several sequences are in the engine at once and share one backing memory for state. | 4 of 6 |
| `state-tiering` | Move per-sequence state out of fast memory to a slower place and back, so that more sequences or longer contexts fit, or so that state evicted from fast memory is restored instead of recomputed. | State in fast memory exceeds what fits, for long contexts or many sequences. | 5 of 6 |
| `prefix-reuse` | Find stored state that a new or resumed request can continue from, and make the sequence hold exactly that state. | always | 6 of 6 |
| `session-persistence` | Write a sequence's whole state to a file and read it back, on request or when a store of reusable state asks for it. | The engine offers saving and restoring sessions. | 3 of 6 |

### Speculation (`speculation`)

Proposing several tokens cheaply and having the full model check them.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `draft-proposal` | Cheaply propose the next few tokens, and when needed their probabilities, for the full model to check. | A cheap source of proposals exists: a draft head of the model, a separate small model, or repetition in the text. | 6 of 6 |
| `draft-policy` | Decide each round whether to draft, from which source, and how many proposed tokens are sent for checking. | The amount of drafting is adjusted while running. | 4 of 6 |
| `draft-verification` | Decide how many proposed tokens the full model accepts, and see that every kind of state comes to reflect exactly that prefix, by committing it or by giving each state's owner the accepted count. | Tokens are proposed ahead. | 6 of 6 |

### Token output (`token-output`)

Turning logits into the tokens and text that are returned.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `sampling` | Turn each position's logits into one token by a chain of steps, with the settings that apply at that position. | always | 6 of 6 |
| `output-constraint` | Restrict or force which tokens may come next, from a rule outside the model: a grammar, a tool-call format, a budget. | The service offers constrained output, or a format that must be enforced. | 4 of 6 |
| `output-interpretation` | Turn produced tokens into what is returned: text, the split between reasoning, answer and tool calls, and the decision where the output stops. | always | 6 of 6 |

### Serving (`serving`)

Everything between a client request and a step of the engine.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `request-front` | Accept requests over the protocols offered, hold the connection, and return results. | always | 6 of 6 |
| `prompt-preparation` | Turn a request's messages, tools and settings into the exact prompt tokens. | always | 6 of 6 |
| `step-scheduler` | Run the engine's loop: decide each cycle what the next step contains, which sequences join it, and what waits. | always | 6 of 6 |
| `sequence-lifecycle` | Own each sequence's life in the engine: admit it, give it a place, keep the record of the tokens whose state is live, pause and resume it, and release it. | always | 5 of 6 |
| `replica-routing` | Present several independent copies of the engine as one, and choose which copy serves each request. | Several whole copies of the engine run side by side. | 2 of 6 (Strata, llama.cpp) |
| `engine-supervision` | Start the engine in order, run its process loop and the transport to the serving side, notice when it stalls or fails, and report it, restart it, or stop it with every request ended. | always | 5 of 6 |
| `scoring` | Compute the model's probabilities for given text or given options, without generating. | The service offers scoring. | 3 of 6 |

### Several devices (`multi-device`)

One model spread over several devices or machines.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `model-partitioning` | Decide how one model is split over several devices or machines, and keep the parts in step. | The model is spread over more than one device or machine. | 4 of 6 |
| `device-communication` | Move activations and partial results between the devices or machines a model is split over. | The model is spread over more than one device or machine. | 4 of 6 |

### Operations (`operations`)

Settings, limits while running, and records of what happened.

| Node type | Its job | Needed when | Seen in |
|---|---|---|---|
| `configuration` | Turn the operator's choices and the machine's facts into one validated set of settings, and refuse combinations the engine does not support or that are known to give wrong output. | always | 6 of 6 |
| `resource-governing` | While the engine runs, keep its use of memory or power within limits: admit or refuse what is asked for, and take back from holders in a fixed order when the limit tightens. | What the engine may use changes while it runs: the system reclaims memory, sequences come and go, or power is limited. | 3 of 6 |
| `telemetry` | Record what the run chose and what it did, in a form that can be attached to the requirements the engine is judged on. | always | 6 of 6 |

## 4. One node type in full

```yaml
id: draft-proposal
group: speculation
summary: Cheaply propose the next few tokens, and when needed their probabilities, for the full model to check.
not: Deciding whether to draft at all, or skipping the proposer when another source suffices, is the draft policy's job.
needed_when: 'A cheap source of proposals exists: a draft head of the model, a separate small model, or repetition in the
  text.'
forms:
- a draft head of the model
- a separate draft model
- lookup of earlier text
- several sources fused per position
takes:
- hidden features or recent tokens
- how many to propose
gives:
- proposed tokens
- their proposal probabilities, when acceptance needs them
effect_on_output: [bit_exact, numeric, distribution_exact, approximate]
rules:
- strength: must
  rule: A proposed token is never returned to the client before the full model has accepted it.
choices:
- what: how many per round
  engines: 3
- what: when a chain of proposals stops
  engines: 3
- what: greedy or sampled proposals
  engines: 4
- what: the set of tokens proposals are restricted to, and whether a cheaper reduced output head is used
  engines: 4
- what: what the proposer needs before it may propose, and what is done when it cannot cover the context
  engines: 2
- what: 'how a lookup source matches earlier text: how far back it searches, the shortest match it extends on, and how many
    tokens it may append'
  engines: 2
seen_in: [strata, ds4, hyperqwen, ninfer, splash, llama-cpp]
```

A field that does not apply is left out; this type has no `owns_state` and no `indirect_effect`.

### 5.2 One node of Strata in full

This is Strata's instance of the type shown in section 4. `settles` lists the choices of the type that Strata decides, with the decision as recorded in Strata's inventory. `own_decisions` counts the further decisions recorded for this part that are not a choice of the type. `described_in` points to the full description of the component.

```yaml
component: mtp-drafter
title: MTP drafter
described_in: comp/strata/mtp-drafter
type: draft-proposal
does: From the verify window's final hidden rows and the tokens that followed them, produce draft tokens with a probability
  each, and keep the draft layer's own attention K/V complete for every accepted position.
settles:
- choice: how many per round
  how:
  - 'Most drafts in one round: the smallest of rows minus 1, the configured cap, and the cells left in the context.'
  - Configured cap on drafts per round.
- choice: when a chain of proposals stops
  how:
  - 'When the draft chain stops before the cap: at the first draft whose probability is below --spec-min-p, or when the
    draft policy''s cost rule says so.'
- choice: the set of tokens proposals are restricted to, and whether a cheaper reduced output head is used
  how:
  - The token subset the draft head covers. Drafts can only be tokens in the subset.
- choice: greedy or sampled proposals
  how:
  - Whether drafts are sampled with the request's sampler chain instead of taken as the argmax.
own_decisions: 4
```

## 6. How this draft was checked

The types rest on parts inventories of the six engines: for each engine, a list of its parts with what each does and which design decisions it makes. The first five engines (240 parts) were used to write the types. llama.cpp (47 parts) was held out, to see how the types fit an engine they were not drawn from (section 6.2 says what I knew of it before the types were fixed).

Who did what. I wrote the types and the assignment of each part to a type, working with Claude. **Every reader named below is a Claude subagent**, not a person: a separate run that sees only the files it is given. The inventories were also written by subagents from the source code, and later readers corrected 58 of their entries against the source.

What the readers were told. The instructions are stored for: matching decisions to choices (`validation/choices/BRIEF.md`) and the checkers of the types (rounds 2 to 7 and the held-out checker) (`validation/CHECK-BRIEF.md`, one file for every run, as it stands now; which version each run saw is not recorded). No instructions are stored for: the first classification run, the classification confirmation, the first selection run, the selection confirmation and the held-out classification on draft 0.8; what those readers were told cannot be checked now. Each future run can store its readers' instructions beside its results (`so_nodetypes_experiments.py instructions DIR FILE`).

### 6.7 Limits

- The readers are Claude subagents (`validation/criteria.yaml`: “Claude subagents (model: opus), each alone in its own folder with only the files named. Not people.”). Two readers of one check are runs of the same model reading the same files, so their agreement with each other says less than their agreement with the key or with Strata.
- The key of 6.1 for the first five engines is my own assignment of parts, and the key for llama.cpp is its held-out checker's (`validation/heldout/check-llama-cpp.yaml`); the answers compared with in 6.4 come from my own description of Strata. All were written from source code.
- Draft 0.9 was not checked against the engines for its rules or its effect on output; the last such check was of draft 0.8.
- Against the pass marks set on 2026-11-16, 21 of 33 figures do not meet their mark, and 3 parts of the marks were never tested. The marks were withdrawn for the thin draft on 2026-11-17, after earlier results were known.
- The readers' instructions are not stored for 5 of the 7 checks (the first classification run, the classification confirmation, the first selection run, the selection confirmation and the held-out classification on draft 0.8).
- The key of the first five engines was revised between rounds, 11 times toward a type a reader had given (37 entries changed in all), and its 240 parts are the ones the definitions were revised against. Agreement on them is not agreement on unseen parts.
- 18 parts of the first five engines and 18 of llama.cpp do more than one job and are allowed any of their types; with the main type only, every reader agrees on 236 of 240 and 40 of 47.
- The held-out check rests on one engine, read in part (15 things not read), and llama.cpp can no longer serve as an engine the types were not drawn from. A further check of that kind needs another engine.
- The fit figures first reported in 6.2 (40 and 38 of 47 plainly one type) were given on draft 0.8; on this draft the readers gave 31, 34, 30, 30.
- The 81 shared choices depend on the rule: 26 with three or more engines, 140 counting loose matches; 55 rest on exactly two engines.
- Each decision was matched to a choice by one reader only. Where two readers judged the same engine's decisions (llama.cpp), one found 36 plainly a choice and the other 60.
- The answers compared with in 6.4 are reconstructions from my description of Strata (the PC and DGX Spark, the DGX Spark one from what Strata's documents report), not observed runs of an engine.
- The files given to the selection readers tell of an existing engine, against the method: first run: 2 lines that name an engine or carry what a removed name left behind, 8 notes on how an engine places or reads the data, the list of engines examined and 7 open gaps; confirmation: 2 lines that name an engine or carry what a removed name left behind, 8 notes on how an engine places or reads the data, `seen_in` on 44 of 44 types and the list of engines examined.
- After the first selection run the conditions of 2 types (`model-conversion`, `row-source`) were reworded on what its readers reported, and the check was run again. Both runs are reported in 6.4.
- 17 of the 44 types have no `needed_when`: every engine has them by definition, so a reader who calls them needed is not tested by the case.

## 7. Not covered yet

Work a general-purpose engine does that no node type describes. All were seen in llama.cpp, after the types were fixed, and are recorded and not added:

- Discovering the machine's compute devices at startup and loading the backend that matches them. Nearest: `configuration`, `device-backend`.
- Producing output that is not text, such as speech, by further models run on the generated tokens. No type is near.
- Composing several kinds of per-sequence state store into one store for a model that needs more than one kind. Nearest: `positional-state-store`, `recurrent-state-store`.
- Cutting one step into sub-steps by the kind of per-sequence state the sequences in it keep. Nearest: `step-execution`.
- Handing hidden features of the full model to a separately run proposer on the device. Nearest: `draft-proposal`.
- Discarding the oldest part of a full context and moving the stored state to earlier positions. Nearest: `sequence-lifecycle`, `positional-state-store`.
- Serving several different models behind one endpoint, loaded and unloaded on demand. Nearest: `replica-routing`.

Seen in one engine only, and kept because no other type does the job: `storage-reader`.

The format that the checking program reads (`ontology/schema.yaml`) still holds the component descriptions of the reviewed version. The node types are a separate file until the list of types is agreed.
