What the Architecture Needs to Explain

The PRD already says what the system should do. This list asks the architecture
author to explain how developers should build the parts and connect them.

Our workflow is: the user submits a research question -> the system proposes an
approach -> generates experiment code -> runs the experiment -> evaluates the
results -> produces a report. The architecture should answer these seven questions.

1. Who does what, and where does the code go?

   Which part calls the model, which runs the experiment, and which checks the
   result? Which parts reuse existing OpenJiuwen code, and which need new code?
   Are they modules in one program or separate processes?
   Developers should know which part they own and which other parts they depend on.

2. How do the parts hand work to each other?

   For example, when the code-generation module hands its output to the experiment
   runner, which files and parameters does it provide? What error is returned if a
   file is missing? Who stops the work if a call times out? What happens if the same
   request arrives twice?
   Both sides need the same agreement so their implementations can connect.

3. In what order does the system run, and how does it stop on failure?

   What must be prepared at startup? When a task finishes, who calls the Gate to
   check it?
   Suppose the Gate returns PASS, but saving that decision fails. The next node
   must not start. Who prevents it from starting, how is the failure recorded, and
   how can the user explicitly restart the work? Explain this sequence.

4. How are files, results and logs stored?

   Where are experiment code, raw output, evaluation results and Gate decisions
   stored, and which part writes each one? How do we tell that they belong to the
   same research run? What happens if the program exits halfway through a write?
   Once the experiment data and scoring rules are frozen, how are later steps
   prevented from changing them?

5. How is AI-generated code restricted?

   Which directories can experiment code read and write? Can it access the network
   or model login credentials? How do we keep code proposed by RSI from seeing the
   hidden test answers?
   Specify the actual isolation mechanisms so developers can implement these limits.

6. What environment does it run in, and where do settings come from?

   Which operating systems, Python versions and dependencies are supported? How is
   the system started, and how are dependencies installed? Where are model connection
   and timeout settings stored? If project settings conflict with user settings,
   which take precedence? When do configuration changes take effect?
   These answers let developers prepare a consistent environment.

7. How can we check the parts separately, then check them together?

   Can we call the Gate on its own, give it an invalid result, and check that it
   blocks the next step? Can we simulate a model timeout and see where execution
   stops? How do we connect all the parts and run the complete workflow?
   The architecture should provide places to invoke components, observe behavior
   and simulate failures. The implementation agent can then write the actual tests
   and commands.

With these answers, the next agent can replace the current pending-design entries
with concrete code locations, interface agreements, implementation steps and test
procedures. Test results can only be filled in after those tests actually run.
