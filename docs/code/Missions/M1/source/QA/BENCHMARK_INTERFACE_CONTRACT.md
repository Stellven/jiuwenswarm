# AI4Research Benchmark Interface Contract

Status: Proposed architecture agreement v0.5 — aligned with Benchmark Requirements v0.12 and the pinned October 8 architecture  
Date: October 14, 2026  
Audience: System architect, PRD lead, verification and benchmark lead  
Scope: One system-wide agreement with Phase 1 baseline/verifier acceptance at M1, Model Routing and RSI benchmarking at M2 and M3, and separately staged extended profiles

AI4Research must make its research system independently measurable as capsules, workflow execution, verification, model routing, RSI, and long-running reliability improve. The benchmark needs controlled inputs and configurations, exact execution records, and sufficient evidence to distinguish module defects from binding errors, gate failures, and unavailable infrastructure. Producing an artifact or declaring success is not sufficient ground truth.

This is the single architect handoff for benchmark interfaces. Sections 3–10 define shared system conditions. Section 11 adds module-specific requirements. Section 12 lists the decisions requested from the architect. The system exposes governed execution and evidence; the independent benchmark owns fixtures, reference judgments, analysis, and scores. The architect's immediate action is to disposition the ten decisions in Section 12, reusing the defined schemas and recording support by delivery profile. The conditions below provide the benchmark context needed for that review.

This contract asks the architect to preserve those evaluation capabilities in the whole-system design, reusing the existing client, runner, gate, and data boundaries. It acknowledges the architecture's exact shared schemas and field contracts, identifies remaining benchmark decisions, and specifies evidence the coding run must provide. It contains no implementation code.

**MUST** means a condition requested by this benchmark agreement. Where the current architecture already defines it, this agreement records that design coverage; where it does not, it remains a proposed addition or decision. Neither status establishes implementation readiness. The architect must give each condition a disposition, owner, source, and delivery point. Unsupported capabilities must remain explicit.

## 1 Benchmark context for the architect

A CC is a reusable capability declaration and implementation package. A node is a product workflow responsibility enclosing a bounded sequence of work and verifier subnodes. The Node Execution Contract pins the sequence, external inputs/outputs, acceptance conditions, and aggregate budgets. Each concrete subnode has its own Subnode Execution Contract and binds exactly one CC. Additional work CCs execute as separately contracted and gated subnodes. Work and verifier identities, subnode gates, and the aggregate node gate must remain distinguishable.

The initial research benchmark evaluates fixed M1 execution: externally supplied correct capsule assignments, an actual library expected to contain roughly 6–10 capsules, a fixed Codex route, independent checks/gates, and zero automatic repair or replay. The benchmark requests `gpt-6.1-sol`; adapter support and effective configuration must be established. Configuration identity and independently verified served-model identity are different evidence. The current delivery build is the complete Intention Compiler node; its smaller build catalogue is reported as observed and does not establish full research library readiness. Static binding performance must not be described as dynamic selection quality.

The initial case uses `screening_capsule` individually and Screening → Hypothesis as a fixed adjacent segment. Other benchmark families assess fixed workflow execution, verifier judgments, route quality/cost, protected capsule improvement, and real 2-, 4-, and 10-hour workloads. All tasks and isolated fixtures represent technology or computer science research obligations.

The architect is being asked to establish interfaces and staged support. Fixed M1 execution remains the initial research benchmark baseline. The complete compiler build can establish shared runtime, library, security, evidence, and client foundations while downstream research modules remain staged. Optional development tools and sidecars are separately scoped and are not benchmark prerequisites or M1 product startup dependencies.

For benchmark acceptance, M1 covers the complete fixed Phase 1 research baseline and all ten Phase 1 Evaluator/Verifier cases in Benchmark Requirements Section 12.1. Model Routing and RSI benchmarking runs at both M2 and M3 because those modules need further development. Static model-call attribution remains M1 reproducibility evidence; routing calibration, savings tests, routing mocks, and RSI improvement/containment campaigns are not M1 benchmark acceptance prerequisites. Conditional dynamic planning/selection/compiler work is Phase 3 Progress; real long-horizon reliability and broader authoring/scale are Extended Performance.

Benchmark milestones and PRD delivery phases are distinct. The supplied product sources retain their Phase 2 RSI and Phase 3 development obligations; this contract follows the user's October 14 benchmark schedule without amending those product sources. Product/PRD alignment sign-off must acknowledge that distinction before a benchmark criterion is promoted into a product release gate. Readiness or performance results for conditional/later profiles do not automatically fail M1 when mandatory Phase 1 baseline and integrity obligations pass.

This interface supports the system-level benchmark of AI4Research. PRD Section 3.7 Scientific Benchmarking is a research-workflow node executing the hypothesis experiment's baseline-versus-treatment protocol. MOD-SU exposes its execution and measurements for independent system evaluation; a scientific improvement alone does not establish a system benchmark gain.

The benchmark owns task specifications, development/evaluation splits, protected reference answers, independent oracles, repeats, and score calculations. The system owns admitted execution, effective contracts, enforcement, capture, gate application, and authoritative state. Protected labels and detailed held-out feedback stay outside capsule, author, verifier, and RSI proposer contexts. Ordinary task inputs remain available to the capsule through its declared interface.

The team has one verification and benchmark lead, responsible for benchmark coordination, fixture/oracle custody, independent evaluation, and reporting. The system architect owns system interface/design decisions, the PRD lead owns product-scope alignment, and module owners supply their integration evidence. The lead coordinates distinct execution and protected-scoring responsibilities under the existing permission boundaries. Independent reference labels and reviewer checks must still satisfy the benchmark requirements.

A valid negative research finding can be correct work. Productive tasks expected to finish and deliberately invalid tasks expected to halt have separate metrics. All scheduled attempts, including failures, timeouts, and environment blocks, must remain visible.

## 3 Responsibilities and permissions

| Actor | Permitted responsibility | Authority excluded |
| --- | --- | --- |
| Benchmark driver | Submit visible inputs to approved profiles, reconcile requests, observe, cancel, and retrieve permitted evidence. | Direct runner calls, gate writes, accepted-artifact insertion, policy changes, activation, production registry mutation, and hidden RSI access. RSI control requires its separately authorized session scope. |
| Verification and benchmark lead acting as authorized evaluation setup owner | Prepare isolated evaluation resources and coordinate approved profile definitions and bounded fault staging with the system architect before execution. | Granting the ordinary benchmark client arbitrary runtime mutation or a gate bypass. |
| Protected binder and runner | Qualify inputs, resolve eligible pins, freeze contracts/check assignments, enforce scope, invoke, and capture evidence. | Selecting protected benchmark answers or accepting producer self-certification. |
| Gate and run-state authority | Assess the exact subject, validate findings, durably record acceptance/halt, and control release. | Treating a client-supplied verdict or native cache as an authoritative pass. |
| Verification and benchmark lead acting as independent evaluator | Read authorized exports and protected references; grade against independent oracles/reviewer labels and retain scorecards outside the evaluated system. | Editing product outcomes, self-certifying a module improvement, or feeding detailed protected judgments into the execution context. |

**BIF01 Shared execution boundary.** Research-workflow and work-CC benchmark runs MUST use the same protected resolver, binder, CC runner, checks, gate host, and evidence/state authority as the corresponding supported system execution. An approved client evaluation entry must not reimplement or bypass those decisions. Verifier replay uses the same supported checking implementations in an isolated evaluation context. Offline RSI uses its architected session controller, write guard, isolated child runner, and protected referee; it is not a production DAG stage. Reuse the audited model/evidence boundaries without treating every hidden RSI helper evaluation as a product work-node gate. Retain the architected local service and scoped client boundary. Work capture, deterministic checking, read-only semantic assessment, protected subnode release, and aggregate node finalization retain their distinct roles. Node finalization aggregates required internal decisions and external outputs without an additional semantic model call.

**BIF02 Protected evaluation separation.** Benchmark expected answers, fault annotations, oracle logic, and held-out scorecards MUST remain in referee-owned storage and contexts. The driver needs only visible inputs and scheduling metadata. Test inputs may be transmitted to the system; protected expected labels may not. Exports must not automatically enter capsule memory, authoring context, RSI development data, or future prompts.

## 4 Required evaluation profiles

**BIF03 Explicit profile support.** The system MUST declare which approved profiles it can execute and their supported revision, readiness, and applicable benchmark milestone/classification. The initial CC benchmark needs individual and segment profiles. The full framework preserves the following entry capabilities, staged by the benchmark schedule and actual module availability:

| Profile | Required behavior | Benchmark applicability |
| --- | --- | --- |
| Individual CC evaluation | Instantiate one work CC under a governed enclosing node and validated subnode binding. Execute required checks, verifier subnode, work gate, and node finalization; retain evidence and end without downstream research stages. One work CC does not mean one total model call. | M1 Phase 1 module pilot; partial-product evidence, not full-workflow acceptance. |
| Fixed segment evaluation | Instantiate a preregistered finite sequence of node/subnode assignments, validate bindings and connections, and execute exact producer-to-consumer handoffs after committed gates. Preserve work/verifier subnode identities, work gate decisions, and aggregate node gates. This does not enable internal CC dispatch or merged CC execution. | M1 Phase 1 module pilot; partial-product evidence, not full-workflow acceptance. |
| Fixed research workflow | Execute the supported governed research lifecycle with a frozen graph and all required stages/gates. It provides end-to-end system evidence distinct from module tests. | Core M1 Acceptance, complete Phase 1 baseline. |
| Verifier replay | Evaluate a frozen contract, artifact, and evidence bundle with pinned checks/assessor configuration in an isolated context. Imported fixture observations never become claimed live observations or production acceptance. | M1 Phase 1 verifier cases plus live enforcement proof; broader/alternate verifier comparisons are progress coverage. |
| Routing calibration/evaluation | Execute matched node items with approved pinned model tiers or routing policies while preserving capsule assignments, input contracts, tools, budgets, and scoring independence. | M2 and M3 Progress, S07 across C01–C08 at each milestone. |
| Offline RSI session | Drive the separately authorized bounded target/profile session through its controller and protected referee, with restricted feedback and no production mutation. | M2 and M3 Progress, S08/S09 on ready targets at each milestone. |
| Long-horizon execution | Run the governed workload with frozen milestones, read-only observation, actual duration accounting, and declared retention/resource budgets. | Extended Performance; real 2-/4-/10-hour tiers are not M1 pilot prerequisites. |
| Controlled fault evaluation | Apply a preapproved bounded fault in isolated evaluation state, exercise the actual relevant validator or runtime boundary, and retain the refusal/failure and effects. Fault setup cannot grant the client release authority. | M1 for Phase 1 binding/gate cases; later routing/RSI fault campaigns follow their M2/M3 profiles. |

Profiles MUST specify allowed input slots, reference bindings or approved pin overrides, required context, checks, limits, tools, effects, and supported capsule kinds. Clients select approved profile identifiers and permitted inputs; they do not supply arbitrary graphs, guard code, model routes, or unrestricted configuration.

Conditional dynamic planning/selection and advanced compiler evaluation need separately declared Phase 3 Progress profiles against the deterministic fallback. A profile's inclusion in the framework does not require its implementation at M1. Discovery and campaign reporting must distinguish scheduled, supported/ready, BLOCKED, and INCOMPLETE coverage with reasons, without replacing the runtime's authoritative lifecycle states. Missing later support does not fail M1 benchmark acceptance; missing mandatory Phase 1 evidence does leave that acceptance unresolved.

A module/segment run MUST carry an evaluation label and an explicit full-product-validity status. Preserving gates does not make a partial segment a full M1 research run. A profile disabling or replacing mandatory controls is an isolated ablation, invalid for product/admission evidence, and is not the initial CC benchmark profile.

**BIF04 Governed fixture qualification.** The architect MUST define how supplied Research Briefs, candidate sets, source snapshots, and other upstream fixtures enter a module profile. The system imports immutable visible resources, records their origin and hashes, validates required contracts, applies the profile's protected qualification/check policy, and records readiness before work dispatch. A benchmark's reference label never establishes system acceptance.

If the system needs an accepted predecessor artifact, choose and document a governed preparation/import route or require an existing accepted artifact. The client cannot insert accepted state. Imported fixtures must be identifiable as evaluation inputs rather than falsely attributed outputs of research stages that never ran. Until that route exists, the relevant module profile is unsupported; running the whole workflow is a separate evaluation with different attribution. Verifier replay additionally distinguishes supplied historical/fixture observations from fresh checking-execution observations, preserves stale/swapped identities for testing, and never silently repairs the subject bundle.

## 5 Client operations and behavioral guarantees

**BIF05 Versioned client contract.** The architect MUST allocate the following semantic operations to the existing application use-case boundary. Transport, command names, URLs, payload fields, and IPC details belong to the owning implementation agreement. RSI operations may share client-adapter conventions, but require a distinct authorized session namespace and custody policy as specified in MOD-RS.

| Operation | Required request meaning | Required response/evidence |
| --- | --- | --- |
| Discover support | Interface revision and authorized workspace/profile scope. | Supported operations, profiles, capsule kinds, schema revisions, measurements, fault capabilities, milestone/classification applicability and readiness, and explicit unsupported items. |
| Inspect library and schemas | Approved catalogue snapshot or exact capsule reference. | Exact declaration, identity/version, admission/standing, implementation/dependency pins, port/schema/check references, and actual catalogue size. Read-only; no semantic selection implied. |
| Register visible resources | Permitted immutable inputs, provenance, content identities, and resource roles. | Scoped resource references, validated hashes, input qualification results, and rejection reasons. Paths must be interpreted in the system's execution environment. |
| Preflight and validate | Approved profile, visible resources, requested pins/seed/budgets within allowed parameters, and pinned execution-environment profile. | Readiness, compatibility, admission/hash checks, fresh hardware inventory and qualification references, required capabilities, measurement/enforcement gaps, and reasons for each block. A preflight is not a dispatch authorization that remains valid indefinitely. |
| Submit | Client request identity, approved profile revision, registered inputs, objective/context, permitted options, and approved campaign correlation where mapped. | Exactly one logical submission outcome: run identity and receipt, or attributable rejection. Effective configuration and freeze references when available; enough correlation to retain the attempt's milestone/domain mapping in the benchmark ledger. |
| Reconcile | Client request identity after uncertain transport completion. | The same submission/run or an explicit unknown/not-created result; no speculative duplicate execution. |
| Observe | Run identity and optional event cursor. | Current authoritative status, correlated events, node/invocation/check outcomes, and next cursor or continuity limitation. |
| Cancel | Authenticated run identity and explicit cancellation request. | Recorded action, observed containment/completion race result, effects already performed, and retained evidence. |
| Export/retrieve | Run/submission identity, allowed audience and artifact/evidence selection. | Versioned manifest, immutable permitted contents, accepted/candidate distinctions, campaign/run correlation, environment evidence, integrity metadata, and omissions with reasons. |

Campaign metadata uses the mapped records in BIF09 or a benchmark-owned ledger linked to authoritative request/run/export identities. The architect chooses the existing field/extension mapping; these additions do not prescribe new API endpoints, arbitrary submission fields, or changes to capsule inputs.

**BIF06 Submission reconciliation.** Request identity MUST map to one logical submission within a documented scope and retention period. Repeating the same request after transport loss must not re-invoke a capsule. Reusing an identity with different content must yield a conflict. Record pre-run refusal even if no run/node identifier was allocated; retain a rejection receipt and enough evidence to keep that scheduled attempt in campaign results.

**BIF07 Lifecycle semantics.** The client MUST distinguish submission acceptance, configuration validation, dispatch, work completion, verification, committed release, halt, cancellation, and interruption. Expose the five exact gate verdicts: `PASS`, `PASS_WITH_KNOWN_LIMITATIONS`, `FAIL`, `ENVIRONMENT_BLOCKED`, and `INCONCLUSIVE`. Expose orchestration actions separately. A pre-run submission refusal may have no run or gate; record that absence explicitly. A protected gate may also halt before work dispatch or without candidate output, using the architecture's genuine failure receipt/checking subject. Export the actual scope, empty/not-run invocation and output fields where appropriate, and real reason; never invent a candidate or a check that did not run.

Headless blocking outcomes MUST return structured non-success without waiting for human input. Client disconnect does not cancel work. Engine interruption remains paused/interrupted with retained evidence and no automatic replay; the client must report that condition rather than wait indefinitely or call it completed. Explicit new repeats or human-corrected runs get new identities and preserve their relationships. Cancellation and completion races follow authoritative committed state, not the last UI event.

## 7 Observation and export requirements

Credentials, control tokens, unrelated account data, and hidden fixture labels must not leak. Producer reasoning or private chain-of-thought is not required to establish correctness.

The campaign ledger must reconcile every scheduled case/repeat with its submission, run/export, pre-run refusal, or explicit not-launched coverage gap. These are staged interface acceptance obligations, not a request to implement all benchmark families immediately. Declare acceptance and blockers per supported module/profile; the complete compiler build can establish shared foundations while later modules remain explicitly unavailable. Its acceptance demonstration includes both internal work/verifier pairs and committed Research Brief release without an extra semantic finalization call. The architect supplies design and ownership decisions; the coding run supplies concrete interfaces and runtime evidence.

A usable individual/segment/compiler interface is a staged integration result, not full benchmark acceptance.
