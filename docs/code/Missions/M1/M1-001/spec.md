## User Scenarios & Testing

### User Story 1 - Start the existing research application in its supported container (Priority: P1)
An operator prepares the pinned application and opens its native UI and control API on the private network. The same deployment can be built for x86-64 and aarch64. Side systems remain optional to product startup.
**Independent Test**: Build the application image for both architectures; inspect image identities; start an identified deployment with the sidecar and RSI absent; authenticate against the same-origin native application. Record actual host and container resources. Native GB10 qualification remains a separate observation from emulation.
**Acceptance Scenarios**:
1. Given a valid protected configuration and private bind address, when Compose starts the app, then its container entrypoint serves the built native UI and control API on port 5173, with the required session authentication.
2. Given missing or invalid operator configuration, when startup is attempted, then execution readiness fails with a stable reason and no governed work is accepted; the application serves the required readiness-refusal/inspection surface.
3. Given stopped or absent side systems, when the app starts, then app readiness does not depend on their installation or liveness.

### User Story 2 - Make an attributable Codex call through the existing adapter (Priority: P1)
A governed caller uses the protected model bridge, a fresh bounded call context and the fixed Codex route. Provider dispatch cannot be invoked through an unprotected alternate path.
**Independent Test**: Connect a real Linux Codex runtime through the secured bridge, execute an authorized headless call, and reconcile its route/call records with its outcome. Separately inject pre-start router failures and a post-start model failure.
**Acceptance Scenarios**:
1. Given valid authorization and available model access, when a call starts, then its immutable route decision and call-start record already exist and identify the effective adapter/model and selected Capsule.
2. Given the API router is off, missing, invalid, killed or late, when a compatible model call is requested, then the fixed Codex choice or attributed Codex fallback is used before call start.
3. Given a selected model fails after call start, when the bridge returns, then the call fails once, preserves evidence and does not switch models or replay the call.
4. Given a verifier call under normal M1 configuration, when routing is requested, then it uses fixed Codex independently of the router's choice.
5. Given an exact registered private E2/E3 request scope, when its fresh model or executor assignment starts, then the same protected native owners enforce its private claims, limits and original deadline, preserve exact evidence and contain only that request. A duplicate/unknown request cannot start again; no ordinary product Run or source attempt is created, altered, restarted or charged.

### User Story 3 - Run generated and candidate-admission work inside enforceable limits (Priority: P1)
Generated POC code, Builder tool commands and author-supplied candidate admission tests operate under a separate executor identity within their authorized workspaces. Their isolation is enforced outside model instructions. The admission provider reports actual test evidence; the Library retains the admission decision.
**Independent Test**: From the actual confined process, attempt permitted workspace operations and prohibited reads, network operations and Docker access. Exercise Builder tool-event limits and inspect cleanup after success, failure, timeout and cancellation.
**Acceptance Scenarios**:
1. Given an authorized workspace, when generated code runs, then it can reach only the declared workspace and permitted resources, with no access to application credentials, state, library, protected fixtures or Docker socket.
2. Given a Builder invocation, when it starts, then it uses one synchronous headless CLI call, the executor identity, workspace-write sandbox, approvals never, tool-command networking disabled and its dedicated protected credential.
3. Given the Builder reaches 40 reported tool calls or its narrower effective limit, when the limit is reached, then protected supervision stops the call as a budget failure and retains the reported events.
4. Given no dedicated budget-limited revocable Builder credential, when Builder readiness is requested, then readiness is blocked; the application's main credential is not substituted.
5. Given an unadmitted candidate and exact shipped fixture or command self-test, when the trusted admission service requests it, then the candidate actually runs in confinement and returns attributable outputs or its declared failure without receiving an admitted execution grant. Unsupported adapters and missing resources are explicit non-successes; a script printing pass is not a substitute for candidate execution.

### Edge Cases
- Missing/invalid/oversized IPC requests, incorrect token, socket ownership mismatch, unexpected runtime version and unauthorized selected-Capsule context must fail without dispatch.
- A router's 30-second deadline is enforced by the bridge, even when the router hangs. Malformed, revoked/unapproved or incompatible choices are rejected before call start. Invalid platform context halts rather than falling back around an integrity failure.
- Route/call-start persistence failure prevents provider dispatch. Missing final evidence is explicit; it cannot be labeled a successful call.
- Transport uncertainty, disconnection, timeout and cancellation preserve attribution and do not trigger implicit resubmission.
- Failure to enforce confinement is a protected security stop. A command denied within an intact boundary is an attributable invocation failure.
- Separate runtime homes do not borrow IDE chat state. Startup does not silently download packages, datasets or models.
- ARM64 image creation, emulated execution and native DGX Spark execution are separate evidence claims. Unsupported hardware or model access remains BLOCKED or NOT_RUN.

## Requirements

### Functional Requirements
- **FR-001**: Extend JiuwenSwarm's existing startup, UI, configuration and Codex adapter rather than introducing a competing application or model proxy. Preserve the pinned OpenJiuwen dependency and existing supported behavior unless a source-backed adaptation is recorded. [PRD 3.0.1; architecture platform/native-reuse.md]
- **FR-002**: Supply reproducible x86-64 and aarch64 application images and a Compose deployment compatible with the app/sidecar/optional human-started RSI topology. Sidecar image content belongs to M1-QA; no side system is a product startup prerequisite. [Invoked prompt; D35/D36]
- **FR-003**: Serve the native UI and authenticated control API on one origin at container port 5173, published only on an explicitly configured private address. Do not expose model IPC, state stores, fixtures or Docker as client services. [PLT-1; M1-006 client agreement]
- **FR-004**: Load one read-only operator configuration, validate its required fields and role aliases, and fail execution readiness closed on invalid configuration while serving the source-required readiness-refusal surface only. Credentials remain protected, outside candidate inputs and published evidence. [PLT-10; reference/field-catalog.md operator-config]
- **FR-005**: Require the secured local model bridge for every governed model call, over owned Unix-domain IPC inside Linux, with socket mode 0600 and ephemeral session-bound credentials. There is no model-adapter TCP listener or broad host-home mount; the executor cannot reach the main credential or IPC. Reuse the existing managed Codex runtime/authentication separation. [PRD 3.0; PLT-4]
- **FR-006**: Write the exact route and call-start provenance before provider dispatch, including the declared/actual Capsule identity, authorization, requested/effective model identity, adapter and available measurement basis. Provider inputs must not gain local telemetry-only metadata. Reliably exposed subscription allowance/limits/credits/reset observations are retained separately as informational account data; they are never represented as per-call tokens or monetary cost. Unavailable usage/cost remains unavailable with reasons. [PRD 4.3.3; model-routing contract]
- **FR-007**: Preserve fixed Codex as the default for all M1 roles. The separate API router is consulted only in an approved enabled evaluation profile; verifier calls remain Codex except under a separately authorized alternate-verifier study. [D44; routing contract]
- **FR-008**: Enforce the router's 30-second pre-start deadline and validate its reply. Missing/error/timeout/invalid-decision outcomes give attributed Codex fallback; platform-integrity failure halts. A chosen model remains fixed after call start, with no implicit replay or switch. [D44; routing contract]
- **FR-009**: Run generated POC commands under a separate OS identity with workspace-only authority, effective resource limits, no protected credential/state/library/fixture/Docker access, and no undeclared network or installation authority. [PLT-3; D45]
- **FR-010**: Launch Builder as one synchronous headless CLI invocation under that identity, with workspace-write sandbox, approvals never, tool-command networking disabled, protected event supervision and at most 40 tool calls or a narrower effective limit. [D43/D45; Builder tool-use sandbox]
- **FR-011**: Require a dedicated budget-limited revocable Builder credential, readable by the executor only for the call and removed from the temporary call location afterward. Never substitute the application's main credential. Retain the explicitly accepted risk that the Builder's own tool command can read its temporary credential. [D45]
- **FR-012**: Report process liveness separately from authenticated model, storage and isolation readiness. Initialize native lossless trajectory capture, adequate trace retention and sandbox activity logging; required raw evidence must survive display truncation. At boot, verify fixture storage is absent or unreadable to both runner and executor; a readable store prevents governed startup. Record actual image/runtime identities and distinguish physical host resources from container limits. Missing prerequisites prevent affected execution without fabricated success. [Client readiness; QA Docker obligations]
- **FR-013**: Preserve original failures and cancellation outcomes. Browser disconnection does not cancel work; application restart must not silently replay an interrupted call. Lifecycle/state integration is owned with M1-002 and M1-006. [PLT-2; failure-and-recovery.md]
- **FR-014**: Provide reproducible build/start/probe/test/export/cleanup instructions that retain evidence. Preparation and cleanup touch only identified task-owned resources and never delete unrelated volumes or disclose credentials. [Invoked prompt; QA Docker environment]
- **FR-015**: Supply a protected pre-admission confined-execution provider for every author-supplied self-test in the pinned declaration. A fixture actually runs the candidate on its exact input; a command drives the candidate and reports its actual end state. Capture the real candidate outputs for pass, or no outputs and its exact declared failure reason. Compare original evidence through the Library consumer, without borrowing an already-admitted grant or replacing independent checking. Missing command, fixture or required model/carrier adapters remain UNBUILT work; missing runtime resources remain BLOCKED. [reference/declaration.md:305,334-343,530; D45; M1-IF-013@r1]
