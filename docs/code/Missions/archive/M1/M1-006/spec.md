## User Scenarios & Testing

### User Story 1 - Obtain the supported outcome (Priority: P1)
The authorized user initializes the server application, receives a session bootstrap, checks observed readiness, uploads permitted research resources, submits via native browser/CLI, observes committed progress, inspects halted or historical evidence, retrieves the final report and artifacts, and controls owned uploads/run data. Stable product identity persists separately from disposable execution workspaces. All clients share the authenticated versioned control boundary; native views project authoritative records.
**Independent Test**: Use frozen source-valid inputs through the actual supported provider/consumer boundary and independently reconcile effects, exact identities, accepted artifacts and persisted evidence. Source/schema fixtures alone cannot establish real external connections.
**Acceptance Scenarios**:
1. Given valid inputs, admitted authority and ready prerequisites, when the scoped operation executes, then Authorized browser/CLI/default TUI surfaces support initialize, readiness, submission, monitoring, inspection and retrieval without changing research acceptance authority.; Duplicate/uncertain submission is reconciled to one run; statuses distinguish accepted/candidate outputs and terminal outcomes; headless clients need no interactive inspection.; Uploaded data and exports remain account/workspace/audience-scoped; own-upload deletion preserves active-use safety and independent captured historical evidence.; Effective operator/user settings and component identities are frozen and observable; account/profile data survives run/workspace deletion; token/credential and hidden-fixture boundaries remain intact.

### User Story 2 - Understand a failed or blocked attempt (Priority: P1)
The researcher or consuming module receives an attributable outcome when required validity, authority, evidence or resources are unavailable.
**Independent Test**: Supply a frozen invalid/boundary counterpart and inspect actual effects, terminal outcome and retained evidence against an independent expectation.
**Acceptance Scenarios**:
1. Given a violated mandatory condition, when the operation is requested, then Invalid authentication, unauthorized workspace/audience, unsafe upload/archive/path, foreign deletion or unsupported operator injection has no unauthorized side effect and returns a stable client-error.; Missing model/isolation/storage/configuration/workspace prerequisite prevents dispatch while inspection surfaces show the actual readiness failure.; Disconnection, stale/malformed status or a successful JSON parse cannot imply completed acceptance; storage failure never claims evidence was saved.; Restart does not replay interrupted work; cancellation is not rollback; corrected work is linked new execution preserving the original failure.
2. Given missing mandatory real service or required unexecuted checks, when status is reported, then it remains BLOCKED, NOT_RUN or INCOMPLETE rather than PASS.

### Edge Cases
The AC table defines source-specific invalid, boundary, failure, cancellation, compatibility and recovery outcomes. Preserve failed/interrupted attempts. Unknown values remain unavailable, never zero. Reused identities cannot replace prior content silently. Missing mandatory evidence is not waived by a generated checklist or summary. Resource blockers constrain affected execution while independent preparation continues.
