# Tools inventory and field enforcement

PRD: 4.1.1, 4.1.2, 4.1.4

> Answers: Which tools does the system need, and where is each Declaration field enforced?

## Purpose

> This page is the single inventory of every tool the system needs. A tool is ordinary code or a service, not a node of a run, so it is not a [capsule](capsule.md#term-capability-capsule). [Declaration](fields.md) is the home of field meaning, [stages](stages.md) is the home of checked and unchecked fields, [runner](runner.md), [runner handlers](runner-handlers.md) and [runner broker](runner-broker.md) are the home of call execution, [toolchain](toolchain.md) is the home of the API detail of the library and run-side tools, and [modules](../system/modules.md) is the home of code placement. The [build order](../build-order.md) is the home of the step numbers. A field marked `checked` is a design and test commitment; it does not by itself prove that every runtime path enforces it.

The verifier is a capsule (`research.verifier`, a skill CC) called at every [Gate](../verification.md#term-gate); it is listed here only because the [Gate host](gate-host.md#term-gate-host) cannot work without it.

## Interface

This page defines no message of its own. Each tool row in the inventory links its schema or names the page that defines its behavior; the schema indexes are [tools](../contracts/index-tools.md), [execution](../contracts/index-execution.md), [services](../contracts/index-services.md) and [library and RSI](../contracts/index-library-rsi.md). Messages that still have no def are listed under [gaps](#gaps-that-must-stay-visible).

## How to read the tables

- **M1 status.** `needed`: the M1 architecture depends on the tool. `manual only`: M1 has the operation but a person [runs](../system/lifecycle.md#term-run) it by command; there is no automatic tool. `future`: outside M1; no M1 module may depend on it.
- **Step.** The step in the [build order](../build-order.md) where the tool is first built. A list such as "1, 3" means the first version is built at step 1 and extended at step 3.
- **Code path.** From the [module map](../system/modules.md), with the M-number from [toolchain](toolchain.md) where it has one. Paths are design destinations, not claims that code exists. A path marked "proposed" is not yet in the module map.
- **Schemas.** Links go to a `$defs` entry in [contracts](../contracts/README.md), or to a type or record page when the value is a [payload type](../types/types.md#term-payload-type) or a stored record. "none" means the tool has no message or API schema yet; the page that defines its behavior is the spec.
- **Tested by.** The demo (D0 to D6) or the invocation surface in [test surfaces](../system/test-surfaces.md). Every tool is first built against fakes of its neighbours.

## Behavior: how the M1 tools work

**Author kit.** Authors run it before they submit. It checks a draft Declaration against the schema and the policy's `required` section. It hashes every file, computes `decl_hash` and `interface_hash`, and runs the capsule's admission checks on its test cases. It should share admission's shape and hash code, so that the two agree.

**Admission.** Its steps are on the [library](library.md#behavior-admission-the-only-way-in) page.

**Runner.** Its full design is on [runner](runner.md). Every capsule call goes through it. It checks the code against the Binding's hashes, checks preconditions, calls the capsule by its kind, builds each output as an Artifact and an Observation, and asks the supervisor, the only store writer, to commit them. A call with no Observation went around the runner.

**Check runner and gate.** Check runners run the checks on an output: `deterministic` and `reference` checks with no model first, then `judged` checks. The gate adds its own fixed checks, `check.call_ok.v1` and `check.within_budget.v1`, folds all results into `pass`, `fail` or `blocked`, as policy `gates` defines, and writes one Verification for each `dispatch` call.

## For imported capabilities (future)

The importer is a future tool. These rules apply when it is built.

- The importer drafts the Declaration, the checks and the test cases. A person or the author kit completes them before submission, because admission needs at least one check and a test case for each admission check.
- One MCP server becomes one capsule per tool it exposes. A2A agents come in the same way, as `a2a` capsules pinned by endpoint and version.
- Every capsule named in `needs.external` is imported and admitted first.
- A receiving system re-admits every capsule under its own [policy epoch](../schemas/policy.md#term-epoch). Another store's Verdict is evidence, not admission.

## What the existing pieces give

- **Permissions and the Codex runtime.** How declarations become permission rules, and why the Codex runtime skips the rail: [permissions](permissions.md).
- **Skill loading.** `SkillManager` already installs skills from online search, ClawHub, SkillNet, team hubs and local folders. An importer would wrap these and add the Declaration and admission. It cannot trust the installed copy's version: a skill's files can change under the same version (`touch_version_metadata`, `server/runtime/skill/archive_store.py:267`, recomputes the checksum and keeps the version). So the hash is taken on a read-only copy.
- **Checksums.** The hub downloader already refuses a package whose SHA-256 differs (`server/runtime/marketplace/hub_package_downloader.py:130`). That proves the download, not the tested code; admission still hashes every file.
- **Sandbox.** jiuwenbox already implements Bubblewrap namespaces, Landlock, seccomp, network isolation and cgroup limits. M1 reuses that confinement engine for restricted children through the restricted child launcher, requiring Landlock `hard_requirement`, an isolated network and the server token, and never its default policy ([process boundary](process-boundary.md#confinement-engine)). Its use as a general verification sandbox that installs `needs.dependencies`, injects `needs.secrets` and enforces `needs.resources` is a future tool.
- **Store.** The Agentic Hub publishes and versions skills, with a ClawHub-compatible API. It stores packages, not Declarations or [Verdicts](../schemas/verdict.md#term-verdict).

A row can be checked at admission without a corresponding runtime guard; the gap column makes that distinction explicit. ## Failure

| Situation | Outcome | Recovery |
|---|---|---|
| A field is marked unchecked at M1 | no admission or run-time effect is claimed for it | treat it as descriptive until the tool that reads it exists |
| A design claim says an effect is enforced | must name the boundary and the covered operation classes | add the boundary, or drop the claim |
| A message has no schema def | its page is the spec until a def exists | add the def and update producers and consumers together |

## Gaps that must stay visible

1. **M1 generated-code confinement:** stage 3.7 needs the distinct unprivileged process boundary in [process-boundary](process-boundary.md); the runner itself is not a sandbox. The confinement engine is reused from jiuwenbox, but general jiuwenbox orchestration (dependency install, secrets, resources) is a future tool.
2. **Other runtime effect enforcement:** admission checks declarations, but runtime enforcement varies by backend. A design claim that an effect is “enforced” must name the boundary and covered operation classes.
3. **Resource and dependency isolation:** CC reads `timeout_s`; it does not generally install pinned packages, inject secrets, or cap CPU/GPU/memory/disk. Stage 3.7's local POC environment is a special PRD-mandated path, not general Declaration support.
4. **Remote identity:** endpoint/version pins are not a live fingerprint check.
5. **Composite contracts:** `members`/`wiring` remain unchecked and have no M1 composer contract.
6. **Messages without a schema def.** The `cc inspect` and `cc artifacts` output and the raw content bytes endpoint have no def in [contracts](../contracts/README.md). The other messages, including the doctor report, the config snapshot, the execution profile and the wheelhouse manifest, now have defs in [`tools-v1`](../contracts/index-tools.md). Each is defined on the page named in the inventory; give it a def before a second module consumes it.
7. **Lifecycle tools:** retries, fallbacks, quality measurement, RSI, import, selection, cost budgets and removal each need a home page, API, records, and failure rules before they can be treated as design-complete.

These are architecture gaps, not implementation-algorithm choices. Resolve them by assigning one home contract page and updating its producers, consumers, gates, fixtures, and system diagram together.

## Placement and enforcement homes

The [module/process map](../system/modules.md) is current for code placement. [Environment](../system/environment.md) proposes actual supported-operation confinement and configuration, and the [model bridge](../system/model-bridge.md) its policy; unsupported profiles fail closed. Admission validates fields; broker authorizes nested/service requests; confined processes enforce filesystem/network access; complete capture records observed effects in required checked Observation.effects_observed and compares them to pinned authorization before success. Automatic librarian drift/Standing action remains deferred. Native permission rails alone are not M1 containment. Required raw capture and model-call counters are M1 requirements; deferred cost estimation/CPU-GPU dashboards do not remove them. [System records](../system/records.md) is the home of dispatch identity, and [storage](../system/storage.md) is the home of crash-safe authority. [Offline RSI](rsi-engine.md) and [measurement protocol](../capabilities/measurement-protocol.md) define the remaining required services. No unvalidated profile is called checked enforcement.
