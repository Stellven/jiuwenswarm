## 1. `factory.inference_lab`

**Materials and behavior.** `cc.yaml:4` packages `METHOD.md`, `SCOPES.json` and `VERIFICATION-UNITS.json`; capabilities occupy `cc.yaml:20`. This is the broad discovery surface: twelve engine layers and five claim classes (configuration, prediction replay, subsystem performance, end-to-end performance, recovery). `test_scope` validates an enumerated claim/layer and returns obligations, limitations and false execution/promotion authority (`experiment_methods.py:4`, `:24`). All other operations delegate: four to methodology, one to hypotheses, two to profiling and one to prediction (`experiment_methods.py:38`). METHOD includes source-method inspiration from MoE-Infinity and Fiddler, explicit GB10 transfer limits, observer failure and ablation practice (`inference_lab/METHOD.md:30`). Paper links are provenance, not imported implementations or inherited results.

**Dependencies and effects.** Wrapper/API dependencies are shared above. Most operations only read reports, but `propose`, `profile_plan`, `analyze_profile` and `evaluate_prediction` persist host observations through their delegates (`hypotheses.py:113`, `deep_profile.py:147`, `expert_prediction.py:178`). Therefore the wrapper's description as “read-only methodology” (`inference_lab/run.py:1`) is incomplete. No operation launches an engine or grants admission. The declared effect is native subprocess execution; durable evidence mutation occurs behind the scoped host API.

**Verification and actual evidence.** The declared unit is a development pytest target, `tests/factory/test_experiment_methods.py`, not an executable domain admission checker (`VERIFICATION-UNITS.json:2`). It tests claim boundaries, unknown claims/fields, inherited evidence scope, native package invocation and refusal to forge scoped host results (`test_experiment_methods.py:9`, `:29`, `:41`, `:62`). The material explicitly says no `factory.cc_qualification` checker admits the package (`VERIFICATION-UNITS.json:12`). Current qualification instead requires another material format and a fixed implementation allowlist (`cc_qualification.py:16`, `:45`); “read unit material” must not be presented as “qualified package.” The newer real Jiuwen proof exercises three aggregate capabilities, including an actual rejected screen; it does not exercise the entire surface.

**Applicability and readiness.** Ready as an advisory aggregate with bounded external modules; twelve layer names do not imply twelve implemented engine subsystems. `test_scope` is layer-independent claim advice, not a hardware feasibility test. Native profiling is Strata-specific; prediction needs a conforming MoE trace; generic methodology is broader but includes six-expert assumptions. The scope and verification material is duplicated in Python constants and can drift (`SCOPES.json:2` versus `experiment_methods.py:4`).

**Improvements.** Make aggregate versus narrow routes explicit in package discovery and annotate which tools persist observations. Declare and hash the delegated implementation closure; expose supported verification units separately from unsupported admission. Generate scope material and runtime constants from one source. Add meaningful aggregate-to-narrow parity checks for returned provenance/authority, especially proposal/profile/prediction persistence, beyond the existing scope-call smoke test.

## 3. `factory.methodology_ablation`

**Materials and behavior.** `cc.yaml:4` includes `METHOD.md`, `ONTOLOGY.json` and `COMPONENT-CANDIDATES.json`; it exports `ablation(evidence_ids, hypothesis_id?)` (`:20`). `run.py:9` routes to `methodology.ablation`. Reports are read from the current task or explicitly readable tasks, with a 4 MiB artifact bound and source-task provenance (`methodology.py:295`). For builtin candidates, the method selects a report-backed ID, rejects unknown IDs and produces either diagnostic AAA or proposed ABBA, at most one changed variable and three trials; `scoring_ready` is always false (`methodology.py:193`). For an explicit persisted hypothesis it validates the proposal/digest/unmeasured state/provenance and returns a design preserving the original counters, falsifier, obligations and applicability (`:237`, `:330`). This second route makes it more than a fixed candidate menu.

**Effects and prerequisites.** Analysis only: it creates no job, task, contract, grant or observation. It depends on scoped evidence and, for authored designs, immutable proposal records. Execution requires host admission, independently valid A/A, a frozen template allowing the selected hypothesis ID, engagement and quiet/resource controls. The separate loop enforces actual execution selection; an ABBA-shaped response is not admission.

**Verification and evidence.** No package-declared verification units. `test_methodology.py:68` covers isolation, trial bounds, false scoring readiness and unknown candidates; `test_hypothesis_ablation.py:21` covers proposal translation, corruption/authority/provenance rejection, explicit ID selection and keeping builtin policy. Its `:108` selection-only tests show an authored ID must be listed in the frozen policy and create zero attempts. Historical real Jiuwen used the narrow ablation path for an unexecuted warmup design (`SPARK-FACTORY-EXPERIMENTS-2026-11-14.md:135`); the newer proof uses the aggregate alias for the screen design. Neither establishes universal causal isolation.

**Applicability/readiness and improvements.** Ready for bounded experimental design. Generic design principles transfer; builtin full-six-expert/Strata assumptions require review on another model. The METHOD's “unknown candidates rejected” text omits the supported explicit proposal bridge. Update it to explain both routes and their separate evidence requirements. Preserve a machine-readable mapping from candidate IDs to adapter/test-template requirements; prevent treating suggested ABBA mode as measured repeatability or scoring permission. Add immutable evidence hashes to ordinary report-derived designs, matching the authored-proposal provenance strength.

## 4. `factory.methodology_diagnosis`

**Materials and purpose.** `cc.yaml:4` packages the same method/ontology/candidate categories and exports `diagnose(evidence_ids)` (`:20`); wrapper `run.py:9` routes to `methodology.diagnose`. Its role is descriptive evidence triage: retain failed episodes, compute raw-timing-preferred decode rate min/median/max, summarize draft engagement, compare repeated prompt/token identities only within comparable configurations, and return ordered investigation candidates (`methodology.py:59`, `:92`). Priorities are recovery, failure, repeatability, then I/O readiness, CPU scheduling, placement and conditional prefill/draft investigation (`:130`). These priorities are hand-coded advice, not a measured causal bottleneck or host-selected action.

**Dependencies/effects.** Scoped report reads, optional authorized historical evidence and the current task objective; no writes or experiment execution (`methodology.py:295`). Up to twenty refs; each report artifact at most 4 MiB. `_rows` understands `measurements` and `results`, otherwise treats an object as one row (`:33`). It does not directly unpack every newer report shape such as top-level `cells` or nested `report`; callers need compatible retained observations/normalization. Metrics can consequently remain absent even when a human can see them deeper in an artifact. Report prose and recorded accuracy labels are never promoted to established semantic accuracy (`:163`).

**Verification and live evidence.** No declared verification-unit material. `test_methodology.py:22` covers unknown versus zero, rate precedence, differing outputs and treatment separation, recovery priority, invalid numbers and tokenized cross-cell identity (`:144`). Provenance/scope tests cover granted historical reports (`:161`). The newer real Jiuwen proof explicitly includes aggregate `diagnose`, proving this shared implementation is usable in a real review loop. This does not verify every source report format or the physical truth of report-provided counters.

**Hardware/model applicability and improvements.** Descriptive rates and evidence triage are general. Builtin candidate generation hardcodes “full-six experts” for prefill (`methodology.py:151`) and its material catalog is pinned to Strata DSV4.1; it needs model-derived expert obligations for other MoEs. Add versioned normalization for actual lab/prefill/benchmark envelope shapes, returning explicit unrecognized-shape diagnostics and coverage counts. Retain report hashes in outputs and make recommendation reasons/order visible as rule identities. Validate prompt/comparison hashes, not only string length, before treating them as experiment identities. Keep missing CPU/I/O counters explicitly unknown.

It also describes a not-implemented discovered component/method candidate. This is report-to-next-input composition, not task creation or implementation.

**Verification/evidence.** No declared verification units. `test_methodology.py:89` exercises two synthetic cycles, preserves the first failure/report and task identity, and changes the next question as evidence changes. `test_methodology_provenance.py:7` checks prior evidence's real source task against the current contract and local same-ID precedence. The newer real proof's follow-up is an agent-published proposal, not proof that `methodology_followup.followup` was invoked.

**Applicability/readiness and improvements.** Ready for proposed-input assembly with the same Strata assumptions as diagnosis. Keep it optional: the agent remains the decision maker. Show the suggested budget as an example constrained by remaining task/operator limits. Explain which candidate IDs are supported and either explicitly support authored proposal follow-ups or reject them with a dedicated error. Retain ordinary report hashes and link retained history rather than allowing a proposed next input to obscure null/failed attempts. ## 7. `factory.methodology_out_of_core`

**Materials and behavior.** `cc.yaml:4` includes method, ontology and candidates; exports `cache_protocol(evidence_ids)` (`:20`), routed by `run.py:9`. It reads/diagnoses evidence then returns a largely fixed two-phase proposal: first request after initialization in a fresh container, then a repeated fixed workload with one warmup and one measured request, up to six completed cells (`methodology.py:179`). Controls cover model/tokenizer/workload, prefix reuse, effective placement/cache/draft state, phase physical reads, headroom, observer cost and absence of builds. It prohibits global cache eviction, treating hardlinks as independent cache and interpreting first/repeat differences as causal A/B benefit. METHOD explains that a model larger than physical memory cannot wholly warm at once (`METHOD.md:3`).

**Effects and applicability.** No cache is touched, no cell launched and no protocol frozen. Relevant to GB10 unified-memory, file-backed DSV4.1 assets and other out-of-core systems when their memory/IO semantics are established. Fresh engine process/container is not cold SSD. A fixed count of one warmup is an example protocol, not convergence evidence; the historical warmup issue is directly relevant. It is not a cache algorithm or placement implementation.

**Verification and live evidence.** No declared verification units. `test_methodology.py:81` verifies bounded cells, fresh container semantics and no global eviction; `:111` proves no dispatch mutations and scope refusal. Historical main-campaign position analysis showed diminishing apparent advantage as baseline warmed and explicitly required a predeclared convergence experiment (`SPARK-FACTORY-EXPERIMENTS-2026-11-14.md:92`). That is a real limitation motivating this method, not evidence its default warmup protocol is sufficient. No reviewed native-call inventory establishes a separate live `cache_protocol` invocation.

**Improvements.** Parameterize phase counts only through explicit predeclared/frozen protocols and include a convergence/stop criterion appropriate to out-of-core working sets. Make the returned protocol's largely fixed nature explicit; currently evidence IDs are attached but measured state does not tailor phase counts. Provide resource- and asset-size applicability fields, physical-read/cgroup/cache boundary semantics, and a deliberate distinction between initialization, filesystem cache and prefix/KV reuse. Avoid promoting any chosen warmup count on post-hoc timing alone.

## 9. `factory.expert_prediction`

**Materials and purpose.** `cc.yaml:4` includes `METHOD.md` and `TRACE.schema.json`; exports `evaluate(artifact_id, k?)`, default k=6 and range 1–64 (`:15`). Wrapper routes to `expert_prediction.evaluate` (`run.py:11`). This is an offline evaluation capability package, not an inference predictor implementation, cache policy or prefetch patch. JSON schema plus Python validator require origin, disjoint train/test request IDs, per-phase/layer increasing token indices, sorted demand and causal issue/readiness timestamps, unique experts and consistent selected/predicted byte counts per event (`expert_prediction.py:21`; `TRACE.schema.json:53`). All training demands must precede every holdout prediction issue (`expert_prediction.py:91`).

**Metrics, effects and limits.** Evaluation compares observed ranked predictions, frozen training frequency with deterministic ties, and causal previous-token history reset per request/phase/layer (`:97`). It reports pooled selected-ID coverage, observed timely coverage, completed-by-demand unused bytes and separately requested-unselected bytes. Counterfactual readiness/waste stay null because their read schedules were not measured (`:146`). It bounds input to 8 MiB, 128 requests and 10,000 events. Dispatch reads a current-task artifact, hashes raw bytes and appends `expert_prediction_offline` (`:165`). It never runs inference, changes routing, claims quality or predicts speed. `origin: recorded` is caller metadata, not authenticated capture, and by-demand unused bytes do not prove lifetime waste.

**Verification and live evidence.** No declared domain verification units. `test_expert_prediction.py:19` is explicitly synthetic: coverage versus timeliness/waste, no holdout training/future demand access, request/phase reset, observed top-k order, frequency ties, leaking/invalid traces, null readiness, scoped origin/provenance and total event bounds. These are meaningful offline algorithm/validation checks. The historical notes explicitly require a live expert-demand/read-readiness emitter before meaningful predictor experiments (`SPARK-FACTORY-EXPERIMENTS-2026-11-14.md:62`); the newer real Jiuwen proof explicitly disclaims expert-prediction benefit. No authentic captured predictor trace or runtime speedup is established by the reviewed evidence.

**Applicability/readiness and improvements.** Ready as a bounded offline evaluator for conforming MoE traces; default six is a convenience, not applicability proof for arbitrary models. Needed next is a provenance-bound emitter with run/request/token/layer/expert/read identities, shared monotonic timestamps, drop/coverage counters and calibrated overhead, all already described by `deep_profile/METHOD.md:39`. Preserve phase/layer and per-request summaries alongside pooled coverage to expose skew. Seal k and split policy before holdout inspection; attach independent capture provenance rather than accepting origin metadata as proof. The runtime only checks selected/predicted byte agreement within one event, so document this granularity and independently validate physical read joins/duplicate traffic before interpreting byte totals as storage cost. Add package verification materials and identify the external evaluator module closure.

## Cross-package conclusions and prioritized improvements

1. **Keep aggregate and narrow packages as deliberate views of the same implementation.** `factory.inference_lab` improves discovery for broad engine work; narrow packages preserve scoped entry points and compatibility. Mark aliases and equivalent implementation identities so an agent does not count their outputs as independent corroboration. The aggregate adds `test_scope`; it does not add a new execution controller or optimizer.
2. **Separate materials, runtime rules and admission checks.** Four narrow packages ship byte-identical ontology/candidate JSONs. The ontology has nine question/signal slices; the candidate catalog lists seven Strata source/knob candidates pinned to `ffa80d73133ea5c548aefe57889a16e8085a938f`, including residency, adaptive cache, CPU threads, prefill chunk, verified drafting, readiness observation and phase telemetry (`methodology_diagnosis/ONTOLOGY.json:1`, `COMPONENT-CANDIDATES.json:1`). Runtime diagnosis instead constructs its own investigation IDs and does not load these files (`methodology.py:15`, `:125`). Thus `strata.prefill_chunk` is material guidance, while `measure_prefill_chunk` is a runtime candidate ID; neither is an admitted implementation. Generate or cross-check these related vocabularies and publish an explicit source-candidate → investigation → admitted-template mapping.
3. **Make verification support honest and usable.** Only the aggregate declares verification material, and that material is explicitly a development target unsupported by current domain qualification. The eight other packages have none. Development pytest coverage is substantial but is not a package-specific unit/admission receipt or scientific qualification. Add scoped verification units, supported checkers and transitive module hashes incrementally; distinguish parser/persistence correctness from observer safety, replay validity and engine benefit.
4. **Normalize actual retained report shapes and bind evidence identities.** Diagnosis currently reads only a small set of report layouts; support the benchmark/prefill envelopes actually emitted and report missing fields explicitly. Ordinary methodology outputs retain source task IDs but not report record hashes, while hypothesis proposals already hash their evidence. Strengthen all outputs to the latter standard without treating hash identity as factual verification.
5. **Resolve actual measurement gaps before expanding optimizer claims.** The retained live-agent screen correctly rejected a faster mismatching candidate. The actual profiler failed. Predictor evaluation remains synthetic until captured event provenance exists. Out-of-core warmup remains a measured confounder. These are useful evidence-driven outcomes, with clear next prerequisites; they are not evidence that these packages deliver sustained performance improvements or weeks of unattended source synthesis.
