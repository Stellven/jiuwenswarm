# Owner design rulings

`Tier 2 · Part of: [Side systems](README.md) · Serves: Standard`

Two side systems come with designs written by their owner teams. Those received designs are kept unchanged in [sources](../sources/model-routing/README.md). This page records each place where this package differs from them, and the ruling. When the PRD and an owner design disagree, the PRD wins. An owner team may ask for a recorded change.

## Routing v2.1

Source: [model router design v2.1](../sources/model-routing/README.md), dated 2026-10-13, technical design, not yet implemented. The rulings below use its section numbers (§). v1.8 is history and no longer the basis of this page.

"Adopted" means the router owns the behavior inside its own process. "Boundary" means the platform rules how the router meets the hot path. Owner text is not repeated here; each row links to its section.

The upstream binder names the Capsule. The router gets the declaration and bound context as given. |
| 24 | Envelope fields | `domain`, `task_category`, `workflow_stage`, `call_function`, host and profile refs, and preferences are runtime envelope fields, not declaration fields ([§2.3.2](../sources/model-routing/received/model-router-design-en-v2.1-2026-10-13.md#232-given-input-and-router-derived-projection)). | Adopted. | 25 | Roles | One Executor type. Protected binding labels are attribution only ([§1.1](../sources/model-routing/received/model-router-design-en-v2.1-2026-10-13.md#11-csml-domain-and-routing-objective), [§2.4](../sources/model-routing/received/model-router-design-en-v2.1-2026-10-13.md#24-routing-profile-and-evidence-contracts)). | Adopted (v1.8 row 6). No client-controlled `role`. `call_function` is attribution, not an executor type. |

## Data Foundation

Source: [Data Foundation for Capability Capsules (M1)](../sources/data-foundation/README.md), Suraj, 2026-09-29, draft. The package fields and layout are in [derived records](../reference/derived-records.md) and the [invocation observation](../reference/field-catalog.md#invocation-observation). The decision is [D37](../method/decisions.md#d37).

| # | Topic | Owner design says | Ruling |
|---|---|---|---|
| 1 | Scope | Capture everything that touched a capsule run. Observe only. Raw material first, structured records built after the run. | Adopted. Raw evidence is kept in per-call folders. The Capsule Run Record and the three derived records are built from it after the run and can be rebuilt. Nothing here changes how a CC, check, verifier or gate behaves. |
| 2 | Hooks never block | Every hook appends to files and never blocks or changes the run. A hook failure is logged and ignored. | Adopted for every hook except one. Evidence the gate needs blocks release when it cannot be written, because the platform commits evidence before a successor is released ([release rule](../reference/derived-records.md#release-rule)). Every other hook, and every derived record, never blocks a run. |
| 3 | Build order | Capture, Run Record, Run Bundle, Conformance, Scorecard, Export, in that order. Library Snapshot is a stretch goal. | Adopted as the order of the record builders. All of them are built in M1 and sit off the hot path. A run works when they are absent. |
| 4 | Record key | When the router gives no execution id, the Swarmflow `agent_id` of the stage's worker is the key. | Not adopted. A framework agent id is never a key. A record is keyed by `run_id`, `node_id`, `attempt_id` and `subnode_id`, and the observation `id` is the invocation id. |
| 5 | Stage is fixed or routed | The record marks `selected_by: static` unless a `RouteDecision` is supplied. | Replaced by `decision_source`, copied from the route record: `router`, `codex_router_disabled` or `codex_router_failed`. It is null when the CC made no model call. There is no `static` value, because the fixed Codex route is already `codex_router_disabled`. |
| 6 | Capsule hash | A capsule is its `.md` file, its Declaration and every file they reference. The hash is over the sorted path and hash of each file. | The package CC is a declaration plus the files in `identity.body`. The record carries `declaration_sha256` and `body_files_sha256`, which is the same sorted path and hash construction over `identity.body`. Together they name the exact version. |
| 7 | Gate gives only a verdict | Per-check fields are recorded as `not_available`. | The gate always produces deterministic check results with check ids. `check_result_refs` points to them. A value that is truly missing is null or empty with a reason, never left out. |
| 8 | Where files live | Everything under `records/` in the project workspace. | `records/` on the persistent volume of the app container. The [layout table](../reference/derived-records.md#records-folder-layout) lists every path. |
| 9 | Run Evidence Capture | Wrapper around each call, gate hook, run-start facts, run-end copies of workspaces, run log and trace data. | Adopted. The CC runner writes the call folder. The gate host writes `gate/`, `verifier/` and `human/`. Run-start facts go to `run-start.json`. Run-end copies go to `run-end/` and `workspace.tar`, made before team cleanup and trace retention. No openJiuwen platform change, no in-run assembly of records and no continuous CPU or GPU sampling, as the owner excludes. |
| 10 | Platform configuration | Lossless trajectory store on, trace limit raised, sandbox activity log on. | A requirement on the platform configuration. If a source is off, the related items are `unavailable` with a reason, and a conformance item for it is `unavailable`. |
