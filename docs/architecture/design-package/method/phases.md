`Tier 2 · Part of: [Method](README.md)`

## Boundaries that remain fixed

- The static template has a separate acceptance record and cannot satisfy the D19 core assignment.
- A new route, compiler or candidate version affects only new attributable runs. It never changes a started invocation, accepted Brief, `run_plan` or historical decision.
- Headless paths never wait. One active run follows one opportunity and hypothesis, with sequential baseline then treatment measurement.
- M1 adds no distributed workers, model training, external publication, live self-installation or recursive improver deployment. Composite creation, merging, arbitrary member graphs and multiple planning epochs remain later work.
- Stage and phase completion need reproducible evidence, not implementation existence or a diagram.
- Implementation status uses `PASS` only for implemented, integrated and verified scope. Unverified work is never `PASS`. `BLOCKED` names an unavailable required dependency. `INCOMPLETE` names behavior not yet demonstrated. This package records `DESIGN` only.

## Stage exit conditions

Predecessor exits govern integration and completion. Independent preparation may start earlier. Each boundary uses admitted capabilities, a protected Node Execution Contract, captured evidence and the same protected gate.

Implementation Stage 1 foundation obligations also apply to every later node. Implementation Stages 3–6 preserve original requests, accepted Brief, source references and protocol where needed; they do not consume only the immediately preceding text summary. Implementation Stage 7 does not delay basic secure startup/headless evidence needed for earlier testing. Implementation Stage 8 independent fixture/target preparation may begin early; full RSI validation requires meaningful baseline evidence. Phase 3 does not wait for Stage 8 (PRD V.10 §6.12).
