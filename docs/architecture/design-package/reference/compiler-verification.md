# Intention Compiler verification obligations

**AI reference and human reviewer context.** [Build entrypoint](../builds/intention-compiler/README.md) defines scope. These are architectural checks to realize in native implementation tests, not a replacement PRD or proof of runtime acceptance.

## Current verifier mode ? 2026-10-21

The user explicitly selected declaration/output-only semantic verification for the current implementation. The assessor receives the pinned Capability Capsule declaration and exact produced output, with independently pinned, input-independent review instructions and criteria. It judges conformance to the declared purpose/outputs/guarantees, internal semantic and structural soundness, contradictions, and stated limitations.

Do not separately disclose user request text, reference documents, accepted predecessor inputs, producer conversation/history, Research Brief as upstream context, runtime observations, policy records, or review-manifest contents. Do not dereference output-carried source references or enable evidence-retrieval tools. Contents already present in the produced subject remain part of that exact output; this decision does not authorize rewriting the subject to hide or improve it.

The protected host retains original input identities, observations, bound checking plans and review-context references for deterministic checks, subject binding, budget/effect enforcement, mechanical assessment validation and gate decisions. These records are not assessor inputs. Every work Capsule still has its required deterministic checks, independent verifier, mechanical assessment checks and protected gate. There is no verifier-of-verifier semantic chain.

Profiles for this mode ask only questions answerable from declaration and output. Do not claim that their semantic PASS proves fidelity to hidden user inputs, preservation of omitted constraints, external citation support or actual scientific truth. Unanswerable assigned questions return INCONCLUSIVE rather than invented support. Comparing with an input-aware assessor is future separately selected work; no automatic switch or input-aware fallback is enabled.

Authority: explicit user instruction in this session, recorded as M1-C020 in the live coding register. This approved narrowing supersedes broader assessor-disclosure language elsewhere in this package for the current implementation; it leaves protected host checks and the POC workflow unchanged.

## Independently assigned criteria

| Subject | Deterministic obligations | Semantic obligations |
|---|---|---|
| Qualified intake | Nonempty request; authorized identity/workspace; configured readable directory; supported/size-bounded required sources; preserved original/extracted references | No model-based meaning judgment during intake |
| Intent IR | Current schema; source/span/ID bounds; permitted identities; completed invocation; effects and limits | Declaration/output conformance; coherent scope/entities; internally explicit uncertainty; workable stated purpose/result. Fidelity and omissions relative to hidden inputs are not assessed |
| Research Brief | Current schema; source/input consistency; unique/resolved obligations; valid typed limits; default authority and actual affected fields; completed invocation | Internally coherent requirement/preference split and defaults; usable stated inputs/deliverables/acceptance/evidence. Preservation of hidden accepted Intent/context is not assessed |
| Verifier assessment | Exact subject/context; every assigned criterion exactly once; reason/evidence; valid verdict; no control action or replacement artifact | No recursive semantic verifier |
| Node release | Required subnode decisions and observed work/review; exact accepted Brief; aggregate budgets/effects; durable evidence/state; required external ports | Reuse recorded Requirements assessment; no additional LLM interpretation |

A profile must explain each criterion, evidence and failure disposition before observing producer output. Bare PASS, producer readiness and valid JSON are insufficient. Missing/duplicate findings, mismatched subjects or nonpassing mandatory checks block release. A verifier reads only the declaration and submitted artifact; original/upstream data remains host-only. It cannot author replacement work.

## Cases and evidence

| Case | Expected behavior / evidence |
|---|---|
| Supported actionable research request | Accepted Intent and Brief, two independent assessments, subnode/node decisions, invocation observations; bounded consumer reads exact released Brief |
| Optional hardware absent | Authorized `single_gpu` assumption points to actual Brief constraint; no observed hardware claim |
| No numeric target/method | Preserve qualitative target/omission; Hypothesis chooses registered experimental procedure later |
| Topic-only or unknown purpose/result | Structurally valid IR may be faithfully extracted but unusable; semantic block, no Requirements invocation |
| Contradiction or invented method/target | Internal contradictions are assessable; unsupported additions relative to hidden input are not established by this mode. No rewrite or autonomous retry |
| Missing specified resource or unreadable directory | Explicit intake/environment error; never represent rejected material as qualified |
| Malformed producer or verifier output | Deterministic halt; bad producer output avoids verifier call; malformed assessment cannot advance |
| Missing/duplicate criterion or stale/swapped evidence | Reject even with an overall PASS |
| Time/call overrun or unavailable endpoint | Halt with observations/failure receipt; unknown token/cost is unavailable |
| Compiler produces no artifact | Record a failure receipt as the check subject; output/accepted inventories remain empty |
| Brief loses a user constraint, defaults purpose, or invents percentage | Preserve applicable deterministic checks. Declaration/output-only semantic review does not prove rejection of hidden-input omissions or additions; reserve that comparison for future input-aware evaluation |
| Node/subnode mixup, cyclic dependency or parent budget exceedance | Reject binding/release; parent does not pool child permissions |
| Failed persistence | No accepted-output publication; preserve candidate/error when possible |
| Cancellation, restart, browser disconnection | No new dispatch on cancel; pause interrupted work on restart; closure alone does not cancel; retain effects/history |
| Image startup/export | Entrypoint starts bundled UI/service/runtime; loopback access works; evidence survives recreation; readable filenames and views match records |

Use the supplied examples for representation/relationships, and labelled challenge cases for model quality. Fixture checks are not measured model behavior; real endpoint evidence is required for successful implementation claims. Keep provider limitations and false acceptances/refusals visible. The downstream consumer is a test boundary, not an implementation of research stages.
