## Controlled difference

Both inputs have the same full-M1 PRD, D1–D18/R1–R8 decisions and exceptions, contracts/versions/field inventory, examples, responsibility/phase tables and assignment limits. Compact retains actual section headings and the newly resolved behaviors; governing principles remain exact. Full offers fuller rationale, walkthroughs and more views. Compact condenses explanation, retaining explicit connected-behavior summaries. It is strengthened for this trial, not deliberately weakened.

The [manifest](m1-comparison.json) freezes all file identities, shared content and counts. [Compression notes](compression-notes.json) identify omitted explanatory blocks/selected views. Counts measure the same 20 explanatory files, including table/diagram text, not total input tokens. Fixed PRD/reference content is deliberately not compressed. Word count alone cannot establish which condition performs better.

## Paired trial controls

Use the [original comparison protocol](../README.md#before-a-paired-trial) for matched tools, implementation base, model/settings, resources and fresh isolated contexts. Give participants only their assigned snapshot, identical PRD/coding rules and the same bounded assignment. Remove access to alternate architecture and evaluator guidance. Pin input hashes after copying. Record unavailable provider identities/seed control and other confounders. Run no participant trial until an assignment/evaluation scope is predeclared.

Predeclare specification-only or implementation evaluation and identical budgets/held-out cases. Clarification answers come from common frozen requirements and are supplied equivalently. A material requirement correction invalidates that pair rather than favoring one condition. Preserve truthful blockers and unrun evidence; don't reward invented certainty. Evaluation is blinded to condition where practical.

## Evaluate both at their best

| Measure | Equal evaluation |
|---|---|
| Compatibility | Invented/missing fields, ports, versions, reference/scope/authority mismatches |
| Whole-system fidelity | Omitted responsibilities, connections, deployment, phases and scientific-negative delivery |
| Failure handling | Unusable/contradictory input, malformed/stale evidence, unavailable dependencies/model/isolation, timeout, storage failure, restart/cancel and RSI security/admission |
| Specifications and implementation | Traceable obligations; lawful private choices; real compatible consumer use and confined effects when implemented |
| Evidence | Exact candidate/configuration/commands/observations; distinguish synthetic, missing, stale and runtime proof |
| Effort | Calls/time/reliable token counts, clarifications, correction/review work; compare only with quality results |

Use the same critical/major/minor severity rules from the original protocol. Repeat across seeds/contexts and distinct M1 assignments where resources permit. An Intent-only success cannot establish full-M1 sufficiency. Record outcomes without assuming that longer or shorter should win. No agent build, human approval or runtime acceptance is demonstrated by these package checks.
