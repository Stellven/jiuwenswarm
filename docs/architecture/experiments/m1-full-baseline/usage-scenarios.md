# Architecture walkthrough routes

**Reading level: human potential.** Question: can the documented connections explain what happens to ordinary and adverse work? The [scenario matrix](coverage.md#scenario-walkthrough) owns expected outcomes; it records no runtime passes.

| Walkthrough | Reading route and what to reconstruct |
|---|---|
| New actionable research request | [Intent](intent-design.md), [workflow](workflow.md), [research](research-design.md): exact input, accepted meaning, requirements contract, frozen work, evidence and delivery |
| Topic-only, contradictory or invented interpretation | [Intent](intent-design.md), [checking fields](reference/checking.md): structure can pass while semantic usefulness fails; protected gate halts before Requirements |
| Valid scientific rejection | [Research](research-design.md), [checking](reference/checking.md): exact registered criteria produce scientific FAIL, infrastructure accepts correct evaluation and delivers it |
| Inspection or interrupted work | [Inspection](artifact-inspection.md), [failure policy](failure-and-human.md): candidate/accepted distinctions, incomplete state, no automatic replay or new execution from viewing |
| Model call or offline improvement | [Routing](model-routing.md), [RSI](offline-rsi.md): shared audited invocation boundary, separate sessions/custody and no referee or activation authority in a CC |
| Container/browser or optional sidecar | [Placement](placement.md), [automation](automation.md): packaged frontend, host loopback, private DNS/client compatibility and separate confinement |

For each walkthrough identify producer, named artifact/fields, consumers, fixed criteria, actual evidence, protected decision and user-visible outcome. If the route requires an unstated assumption or invented payload, deepen the relevant design/reference rather than append an unrelated process card.
