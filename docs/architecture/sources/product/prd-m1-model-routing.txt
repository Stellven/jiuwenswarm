### 3.X Foundational Models & Routing

#### 3.X.1 Model Capability Registry
- **Definition & Expectation:** Record declared and verified model capabilities such as modality, context size, tool use, structured output, cost class, and suitable tasks [cite: 10].
- **Whitelist (M1 Scope):** API-based registration of Codex, Qwen, DeepSeek, GLM, Gemini, OpenAI GPT-series models, and a small curated set of domain-specialized academic models covering areas such as coding, mathematics, scientific reasoning, biomedical research, and other research-intensive domains. Each registered model maintains lightweight capability metadata used by the routing layer.
- **Blacklist (Excluded from M1)**: Large collections of narrowly specialized models; numerous fine-tuned variants of the same base model; task-specific checkpoints with limited general applicability; experimental or poorly documented models without stable API access; locally hosted model weights; and exhaustive coverage of every available model family or version.
- **Dependencies:** API key and endpoint provisioning; a minimal and consistent model capability schema.

#### 3.X.2 Model Routing & Selection
- **Definition & Expectation:** Match and select a model route using task needs, capability, quality, cost, policy, quota, and current health. Allow models to obtain tasks in their advantaged field [cite: 10].
- **Whitelist (M1 Scope):** Lightweight two-stage routing. The Router first selects a single Capsule based on the task and execution role, then filters and selects the most suitable compatible model for that Capsule. Model selection uses capability metadata together with lightweight LLM-based judgment. M1 supports API-based model access, deterministic compatibility filtering, routing for Planner, Coder, and Reviewer roles, and simple fallback to a predefined compatible model when routing fails.
- **Blacklist (Excluded from M1):** Learned or fine-tuned routers; model embeddings or vector retrieval; GraphSAGE, HNSW, or other large-scale retrieval infrastructure; bandit, reinforcement-learning, or online-learning-based routing; multi-model voting or ensembles; mid-execution model switching; complex global cost/latency optimization; dynamic multi-agent team formation.
- **Dependencies:** Model Capability Registry; Capsule Registry; API access to candidate models.

#### 3.X.3 Model Usage Auditing
- **Definition & Expectation:** Record model calls, routes, users, tokens, cost, quota consumption, and policy decisions for audit and accounting [cite: 10].
- **Whitelist (M1 Scope):** Record the selected model, selected Capsule, task and role, timestamp, token usage, estimated cost, execution success or failure, and whether fallback occurred for each routed model call.
- **Blacklist (Excluded from M1):** Full billing integration; organization-wide quota enforcement; advanced policy compliance analytics; long-term usage optimization; cross-user chargeback; real-time anomaly detection.
- **Dependencies:** Routing output metadata; model API usage and token statistics.

#### 3.X.4 AI Reviewer Agent (Routing Integration)
- **Definition & Expectation:** An AI-driven Reviewer Agent embedded within the routing workflow to independently assess the quality and correctness of implementation results using a routed Reviewer model and Capsule.
- **Whitelist (M1 Scope):** Route Reviewer tasks through the same Model + Capsule Router; independently review Coder outputs for correctness, regressions, and compliance with task requirements; return structured review results without modifying the implementation.
- **Blacklist (Excluded from M1):** Reviewer-driven rerouting or model switching; automatic code modification by the Reviewer; multi-reviewer voting or ensemble review; autonomous iterative Coder–Reviewer loops.
- **Dependencies:** Model Routing & Selection; Reviewer Capsule; access to implementation outputs and relevant task context.
