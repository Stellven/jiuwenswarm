# 20261113 Contract and Engine Ontology prepresentation

The system ontology describes the engine's structure. The detailed node slice `expert_weight_readiness` links the method to a small portion of that structure. Its eight regions are L4.router, L4.selected_expert, L4.expert_execution, M.expert_weight_range, M.read_request, M.readiness, M.page_cache and M.memory_budget. It also names seven quantities, including fill.decode_bytes_read, fill.demand_wait_ns_per_token and decode.ms_per_token (`context/expert_streaming/ONTOLOGY.yaml`, `slices:`). L4 means model operations, L5 means kernels/runtime, and M denotes cross-cutting memory and storage concerns. These are ontology identifiers, not execution order or neural-network layer numbers. Named identifiers are more stable than renumbering historical diagrams.

An engine node is a part or property of the engine. A work node is a proposed action such as inspect, integrate, build or evaluate. The new optional engine_slice reference links the two. The task's planning constraints select the slice; the frozen lab contract separately fixes the workload and output reference. Do not claim the historical experiments were generated by this newly added link.

| Layer or box | Existing behavior | CC intervention | Evidence |
|---|---|---|---|
| L4.router / selected expert IDs | Routing chooses experts | Hooks expose IDs and predictive routing can anticipate the next layer | Source callback and prediction counters |
| M.read_request / page_cache | Compute can fault on mapped weight pages | Demand fill reads selected ranges; predictive reads request ranges early | Fill activity, bytes and demand wait |
| M.readiness | Needed pages may arrive late | Optional readiness instrumentation distinguishes prediction from arrival | Readiness counters, separately captured when enabled |
| L4.expert_execution / L5.cpu | CPU consumes expert tensors under -cmoe | Same computation consumes prepared pages | Identical fixed-prompt output and decode timing |

The relation is contract → target slice → CC choice → source changes → image → observations → decision. A slice reference validates the declared target and keeps it visible in the work graph; it is not proof that every code edit respects a complete semantic ontology. The ontology remains provisional. Current capsule 2.0.1 / ontology 0.2 adds this linkage after the recorded runs; their capsule version was 2.0.0. The frozen cc-rsi-v1 reference is unchanged.

## What the new slice link actually does (code)

It was added on 13 Nov at 07:36 in jiuwenswarm `6d10c8c5`, with capsule 2.0.1 and ontology 0.2. All paths below are in jiuwenswarm.

- **Validation.** `factory/ontology.py` loads ONTOLOGY.yaml. It requires each slice's regions and quantities to exist in the vocabulary. `validate_slice()` rejects unknown slice names.
- **Seeding.** `factory/taskgraph.py` `initial_plan` reads `task.constraints.engine_slice`, validates it and copies it onto every seeded work node. It also adds `contract:<contract_id>` to each node's inputs.
- **Plan edits.** `plan_patch` add and update operations validate any `engine_slice` they carry.
- **Tasks without a slice.** They are unchanged.
- **What reads it.** Nothing in dispatch, build, lab, gate or acceptance code. The agent sees it only through plan nodes and the capsule guidance (`STREAMING.md`, "Name the engine target, then revise the work").
- **What it does not do.** It does not verify semantically that a code edit stays inside the slice.
- **Tests.** `tests/factory/test_ontology_dispatch.py::test_engine_slice_target_and_contract_link` covers seeding, the contract input, patch add, rejection of an unknown slice on update and on seed, and absence without the constraint.
- **Historical runs.** Neither J-OM13 nor the fresh recording (capsule 2.0.0, 13 Nov 02:47–03:40) used this link.

The source map in context/expert_streaming/SOURCE-MAP.md names the actual callback, tensor offsets and integration sites. Its line numbers belong to its stated revision, not arbitrary current HEAD. The console's engine diagram is a selected MoE decode path, not a complete sequential execution diagram of all llama.cpp operations.
