The engine’s own request scheduler is unrelated to the factory’s job scheduler. Branch ai4r/iterative-cc-factory, from AI4Research-Main 141c1c4.

The task arrives as a contract: what to achieve, what must not change, the frozen output check and the budget. It does not fix the route. The engine ontology is a small vocabulary of the engine: router, selected expert, weight range, readiness, where computation runs, and the quantities we can measure. The capsule uses it to explain which component addresses which quantity, and the evidence tool uses it to keep "predicted the right expert" apart from "its weights were ready in time". The loop: the agent chooses the next useful work, and the task graph records it as revisable work rather than a frozen plan. The job queue makes sure only one heavy thing runs on Satay at a time. The capsules do the actual integration, build and lab runs. Each result is assessed by the rule that fits the module: a performance component must be faster, an observability component must deliver its signal within an overhead bound. Everything goes into the shared evidence store, and the next decision queries it. In Run 5 you will see the graph change when a measurement turned out to be impossible as planned. What we reused: the existing controller, store, durable jobs, image admission and CC runtime. What changed: the old freeze-then-execute policy is replaced by this revisable loop, as recorded in the design-change note.
