## User Scenarios & Testing
### User Story 1 - Offline implementation-only capsule improvement (Priority: P1)
A researcher can evaluate a bounded child of a permitted capsule offline, inspect evidence and later choose whether to activate it through the existing admission/activation process.
**Independent Test**: Given a permitted target and properly seeded, isolated fixtures with baseline headroom, when the offline loop runs, then evaluate compatible children against fixed parent comparisons without exposing hidden inputs, changing the live workflow or activating a child. If fixture headroom or permission is absent, stop the affected run with evidence.
**Acceptance Scenarios**:
1. Given source-conforming inputs and ready declared dependencies, when this bounded capability executes, then its artifacts and observable effects satisfy the ACs below and remain attributable to the run/capsule.
2. Given a prohibited action, invalid contract/evidence or source-defined failure, when execution or verification detects it, then preserve the failure and follow the shared halt/non-admission behavior; do not silently report completion or repair autonomously.
3. Given a connected consumer, when the provider submits an artifact/candidate, then respect the owning interface, governance boundary and version identity rather than infer success from a model response.

### Edge Cases
- Run paired parent/child checks with versioned same-fixture inputs and exactly three repeats; inspect mutation scope and deterministic score production. Submit dimension-change and AI-judge requests as planted invalid proposals.
- Use paired scoring fixtures where pass counts differ and where they tie; inspect selected result and timing evidence to verify faster time cannot override fewer passed tests. Inspect runtime configuration before/after.
- Generate permitted one-file and planted multi-file/schema/operator children; inspect diffs, interface identity and parent-suite outcomes. Reject incompatible/forbidden changes; bind performance expectations to the fixed source policy and target benchmark.
- Replay a compatible child on recorded inputs, then run actual type/wiring validation without executing live workflow nodes. Inject a mismatch/role-or-gate mutation and verify it is not accepted.
- Exercise a visible-regression child, a hidden non-winner, a legitimate improvement and planted forbidden-access/policy-mutation children against the actual scorer and isolation boundary. Assert outcomes from fixed fixtures rather than implementation-derived expected values.
- Produce and inspect a legitimate chain and planted broken-lineage/tampered-score cases; verify invalid provenance prevents candidate submission. Inspect product memory for absence of RSI lesson writes.
- Inspect loaded dependencies/calls and session model identities; attempt prohibited trainer/fine-tune/model-switch actions through safe fixtures and inspect exported training-ready pairs without executing training.
- Test below/exact/above fixture-count and headroom boundaries, overlapping and independent splits; inspect programmatic halt versus permitted start. Run end-of-loop attribution checks reverting each lineage step and retain outcomes without exposing hidden contents to the proposer.
- Prove permitted aggregate-only scoring and denial of hidden input/output access; exercise query 30 and attempted query 31, verify fresh process execution and unchanged live artifacts/active pointer. Submit a valid candidate to the real admission interface without activating it automatically.
Architecture supplies representation, timeout/cancellation and recovery details; there is no assumed retry or resume mechanism. Source-specific numerical limits are listed in ACs only. No real-service claim is established by fixtures or stubs.

## Requirements
### Functional Requirements
- **FR-001** (§4.4.1): Permit only authorized implementation prompts/internal rubric text, scales and weights; preserve the core rubric dimensions. Compare parent and child on exactly the same offline fixtures with k=3 repeats; no AI-judged scoring, live/shadow A/B or multi-child GEPA/MIPROv2 populations.
- **FR-002** (§4.4.2): Record execution traces, call counts and cost.time_s per proposal; use time only when versions pass the same number of tests. Do not optimize budgets/timeouts, route models, switch models mid-session or run concurrency load testing.
- **FR-003** (§4.4.3): Allow Python helper evolution only inside the capsule sandbox copy with one code-file change per child and unchanged interface_hash. Apply parent-suite compatibility and strict lower-bound performance/regression checks. Exclude multi-file code changes, contract/schema mutation and physical workspace-I/O operator mutation.
- **FR-004** (§4.4.4): Keep workflow structure and agent roles read-only; perform recorded-node-input replay and a non-executing DAG wiring dry-run with zero port-type mismatches. Exclude role reassignment, workflow evolution, gate additions/removals, AFlow/MCTS/ADAS search.
- **FR-005** (§4.4.5; §§2.8,2.11): Keep the referee immutable: zero regressions on visible tests, win the hidden loop set, use time only as the prescribed tie-breaker. Use planted bad children/golden sets and CI violation tests to show forbidden accesses are blocked. RSI cannot edit Gate, Verifier, checks, sealed suites, policy epochs or reward model.
- **FR-006** (§4.4.6): Maintain RSI-only hash-chained attempt logs, parent_hash lineage and bound candidate evidence; pre-submission checks verify resolvable lineage and logged-versus-claimed scores. Do not write lessons to product memory or add memory learning, Self-RAG or reranker training.
- **FR-007** (§4.4.7): Mutate only code/text, keep model weights unchanged, import no trainers and call no fine-tuning endpoints. Pin one model per session and export rsi_pairs.jsonl for future human-led work; no SFT/LoRA/DPO/GRPO/Agent RL or routing-policy tuning.
- **FR-008** (§4.4.8): Maintain per-target dev/hidden-loop/hidden-final split manifests with zero hash overlap; manually seed at least 20 loop and 20 final fixtures. Halt at session start unless the baseline fails at least 20% of the hidden set and at least 5 final cases. At close run lineage-step-reversion ablations. No self-authored hidden fixtures, adaptive curriculum, active learning or external benchmark tuning.
- **FR-009** (§4.4.9; §2.11; §6.11): Operate only in the offline local sandbox with hidden fixture records outside the public repository and inaccessible to the proposer. An independent oracle runs children in fresh subprocesses and exposes aggregate pass/fail counts only, capped at 30 queries/session. Output an evaluated candidate for human review/activation through M1-003, never auto-deploy or upstream-publish. Do not claim jiuwenbox network confinement for this M1 RSI path.
### Key Entities
Parent and child capsule implementation; unchanged interface_hash; visible/dev, hidden loop and hidden final split manifests; Fixture Oracle; aggregate scores; hash-chained attempt log; parent_hash lineage; cost.time_s; rsi_pairs.jsonl; candidate offered for admission.
