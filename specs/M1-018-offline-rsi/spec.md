## User Scenarios & Testing
### User Story 1 - Required bounded code improvement (Priority: P1)
A researcher uses a fixed offline engine to propose/evaluate an authorized child of the pure rank_opportunities helper in a sandbox copy of screening_capsule while the production helper/live workflow remain unchanged.
**Independent Test**: Use a stable permitted parent, declared profile, fixed independent referee and independently frozen protected fixtures. Parent tests/compatibility must pass before hidden improvement evidence. Compare under the same declared model/runtime where applicable; output an inactive sandbox child with attributable evidence.
**Acceptance Scenarios**:
1. Given eligible Target 1, when only the authorized helper changes, then fixed dimensions, Top-1/Opportunity_Card.json behavior and effects remain invariant.
2. Given scope escape, hidden access, permission expansion, referee/evidence tampering or promotion bypass, when detected, then block, halt the affected session and preserve attributable evidence; autonomous continuation requires explicit human clearance.
3. Given an evaluated candidate, when submitted to M1-003, then admission and human activation remain separate from RSI and human rollback remains available.

### User Story 2 - Conditional authorized text improvement (Priority: P2)
A researcher evaluates authorized screening implementation text using the same fixed engine/profile approach if bounded headless model execution is available.
**Independent Test**: Record dependency availability. If available, compare paired parent/child text on the same permitted fixtures/model/runtime. If unavailable, record M2 deferral without blocking required code/guardrail acceptance.
**Acceptance Scenarios**:
1. Given explicitly mutable SKILL.md/references/rubric.md fields, when permitted implementation content changes, then required dimensions/interface/parent tests/referee rubrics remain fixed.
2. Given no bounded headless path, then record deferral rather than fabricated execution or M1 release blockage.

### Edge Cases
- Missing eligibility; self-expansion of tool/network/resource/evaluation/promotion permissions; dimension/interface/effect changes; multi-file/helper-external/operator/dependency mutation.
- Faster child with fewer tests passed, parent failure, good/bad candidate cases, referee/scoring drift or incomparable model/runtime.
- Insufficient fixtures/headroom; protected/development overlap, hidden contamination/rewriting, tracking feedback, loop-cap excess or early/repeated final assessment.
- Hidden contents/answers/identities/per-case results leaking through context/logs/output; unauthorized filesystem/process/tool/network effects; resource exhaustion; audit tampering; prompt-injection scope escape.
- Automatic resume after a violation or automatic exception; self-promotion; failed activation; explicit human rollback.
- Unresolved lineage, inconsistent claimed scores, absent run-derived observations or falsely labelled conditional Target 2 completion.

Architecture owns representations, failure/cancellation/restart wiring and actual isolation realization. No former r1 quantitative defaults are inherited.

## Requirements
### Functional Requirements
- **FR-001** (§4.4.1): Conditional Target 2 mutates only explicitly authorized implementation prompts/rubrics, preserving dimensions/interface/parent tests and paired same-fixture evaluation. Work-capsule rubric permission never extends to referee rubrics. No populations, live/shadow A/B, cross-node text optimization or LLM-judge loss objective.
- **FR-002** (§4.4.2): Record proposal traces, call counts and time (cost.time_s); time only breaks exactly equal pass-count ties. No budget/timeout/routing/model-switch/concurrency optimization.
- **FR-003** (§4.4.3): Required Target 1 changes only permitted pure rank_opportunities code in a screening sandbox copy. Production helper, dimensions, Top-1/Opportunity_Card.json, checks and effects stay fixed. Parent tests/compatibility precede hidden evaluation. No multi-file/operator/dependency/whole-workflow evolution or automatic adoption.
- **FR-004** (§4.4.4): DAG/roles remain read-only; recorded-input node replay and non-executing wiring dry-run show zero port-type mismatches. No role/workflow/gate evolution.
- **FR-005** (§4.4.5): Independent referee/check runners/hidden sets/scoring/promotion policy remain immutable. Freeze scoring before session; pin relevant referee configuration to detect drift. Mandatory parent behavior/tests precede improvement; loop feedback bounded and final assessment terminal-only. Independently supplied good/bad/security cases validate behavior; no self-generated acceptance or uncalibrated judge-only target.
- **FR-006** (§4.4.6): RSI-only hash-chained attempts, parent_hash lineage and candidate-bound evidence; pre-submission provenance checks resolving lineage/claimed-log scores. No product-memory lessons, memory learning, Self-RAG or reranker training.
- **FR-007** (§4.4.7): Only code/text mutation; no RSI training/weight modification/fine-tuning endpoint control. Valid parent/child comparisons use the same declared model route/relevant runtime and record identity/available metadata. Optional training exports remain separate future human-led work, never RSI weight updates; no mandatory export filename or RSI Verifier calibration.
- **FR-008** (§4.4.8): Separate target-specific development/hidden-loop/hidden-final splits; tracking outside optimization. Zero known protected/development overlap and independent split custody. Manually seed approved minimum hidden fixtures before sufficient telemetry and preserve baseline headroom. Record attempts/lineage/outcomes/time/session state and available joinable platform references. Check coverage/contamination/provenance/replay/attribution; no self-authored/selected hidden data or adaptive curriculum.
- **FR-009** (§4.4.9; §§2.11/6.11): Offline execution separate physically/logically from live DAG; proposer/candidate cannot read protected hidden/scoring material or share its authoritative trust boundary. Freeze sets before session, expose only approved bounded aggregates, cap loop use and terminal final assessment. Preserve attributable activity. Consume §§5.2.1/5.4.3 provisioning/startup constraints without prescribing realization.
- **FR-010** (§4.4 introduction/4.4.3; §§1.3/6.11): Improver stays fixed; shared loop target-independent; target profiles own fixtures/scoring adapters/mutation permissions/proposer settings. Target 1/security required for M1; Target 2 conditional/non-blocking if deferred.
- **FR-011** (§4.4.10; §§2.11/6.11): Fixed source threat model and intentional adversarial suite. Every mandatory case blocked with attributable evidence; violations halt session and require explicit human clearance. Reconcile authoritative records, prevent hidden disclosure, record discovered vulnerabilities/limitations/residual risks. No automatic exceptions or self-certifying hidden security tests.
- **FR-012** (§§4.1.5/4.4.9/6.11): Child remains inactive until required admission/explicit human activation through M1-003; human rollback available. No autonomous promotion/activation or promotion-control mutation.
