## User Scenarios & Testing

### User Story 1 - Integrated M1 governed research and workstation verification (Priority: P1)

Whole-system journeys and cross-cutting invariants for the complete required M1 scope: Phase 1 research/workstation and the separate required offline RSI validation track. Child feature requirements remain in their owning specs.

**Independent Test**: Run the assembled candidate on the complete journeys below; no single component suite substitutes for this result.

**Acceptance Scenarios**:

1. Given the prerequisites for AC-001, when its planned action is exercised, then the observable result must satisfy AC-001. Procedure: On an identified assembled candidate, submit permitted local research/code/data assets and a bounded objective; execute 3.1 through 3.9 with actual configured provider and permitted connectors. Inspect ordered artifacts, a positive scientific verdict supported by the frozen protocol, gate decisions and final delivery; neither canned JSON nor a stub-only DAG establishes this AC.
2. Given the prerequisites for AC-002, when its planned action is exercised, then the observable result must satisfy AC-002. Procedure: Use a pre-registered scientific contract and a test case expected not to satisfy it; compare empirical evidence, scientific verdict, infrastructure gate and delivered report. Independent fixtures may be developed in plan without inventing production thresholds.
3. Given the prerequisites for AC-003, when its planned action is exercised, then the observable result must satisfy AC-003. Procedure: Integrate M1-007 acceptance cases with actual producer/harness/evidence consumers. Inject invalid schema, swapped run/capsule identity, unsupported citation, budget overrun, forbidden action and delayed persistence; inspect downstream-start absence and attributable terminal state.
4. Given the prerequisites for AC-004, when its planned action is exercised, then the observable result must satisfy AC-004. Procedure: Capture the scientific contract before POC generation, run the connected experiment, compare immutable components and observed tools/artifact writers, and attempt prohibited downstream mutation using controlled fixtures.
5. Given the prerequisites for AC-005, when its planned action is exercised, then the observable result must satisfy AC-005. Procedure: Exercise source-permitted local resources and bounded academic retrieval on the real candidate, then probe disallowed acquisition/actions in a disposable environment; compare observed effects with permissions and gate outcomes.
6. Given the prerequisites for AC-006, when its planned action is exercised, then the observable result must satisfy AC-006. Procedure: Follow inputs, run/stage/capsule identity, raw logs and both gate tiers from execution into durable bundles; inject Tier-1 failure and attempted reviewer modification, then inspect model calls and artifact changes.
7. Given the prerequisites for AC-007, when its planned action is exercised, then the observable result must satisfy AC-007. Procedure: Induce an unavailable dependency and execution fault on the connected candidate; inspect human_session behavior and retained fault record, then perform only the source-authorized explicit restart and inspect its evidence. Exact restart mechanism awaits Architecture.
8. Given the prerequisites for AC-008, when its planned action is exercised, then the observable result must satisfy AC-008. Procedure: Execute clean installation/startup and a user journey on each confirmed source-supported platform; inspect authentication, CLI/Web/TUI events, artifact retrieval and tmux operation using M1-017 and M1-002 evidence without duplicating their feature ACs.
9. Given the prerequisites for AC-009, when its planned action is exercised, then the observable result must satisfy AC-009. Procedure: On the same versioned release candidate, run the source-bounded RSI path using hidden fixtures and then a baseline workflow; inspect version lineage, unchanged policy and unchanged active pointer during the RSI loop, followed only by explicit human activation/rollback and explicit activation history. Reuse corresponding child evidence only after candidate equivalence assessment.
10. Given the prerequisites for AC-010, when its planned action is exercised, then the observable result must satisfy AC-010. Procedure: Inspect actual default configuration, reachable features and parent allocation; run required static research/workstation and offline RSI validation without Phase 2 and verify neither requires experimental completion.
11. Given the prerequisites for AC-011, when its planned action is exercised, then the observable result must satisfy AC-011. Procedure: Audit the full source-to-AC allocation and candidate manifest before the final system run. Identify each source/architecture/interface revision, changed execution input and required child evidence; record unresolved source changes rather than treating them as passed.
12. Given assembled headless evaluation and a blocking stage/Gate condition, when executed, then AC-012 returns machine completion without human waiting, preserves durable Gate lock and records actual configuration/requested-effective seed. Documentation checks do not establish runtime acceptance.
13. Given approved preregistered Gate-disabled ablation, when evidence is produced, then AC-013 labels evaluation state and excludes product/Definition-of-Done acceptance or automatic production activation.

## Requirements

### Functional Requirements

- **FR-001** (§1.1, §1.2, §1.5, §6.2, §6.5, §6.6, §6.7, §6.8, §6.9): One real user objective with a scientifically positive outcome traverses the fixed intake-to-report research journey with the PRD-required brief, candidate set, selected opportunity, immutable hypothesis, POC bundle, benchmark evidence, scientific verdict and local report, with governed handoffs evidenced.
- **FR-002** (§1.4, §1.5, §2.5, §6.8, §6.9): A correctly executed scientific negative result remains negative and reaches Delivery when infrastructure admissibility passes; it is not silently converted into a positive claim or treated as execution failure.
- **FR-003** (§1.4, §1.5, §2.8, §6.4): Invalid, stale, unsupported, prohibited or otherwise inadmissible artifacts cannot advance the assembled workflow; required gate evidence is durable before a dependent node starts.
- **FR-004** (§1.4; §2.5-§2.7; §3.5.4 (lines 761-768); §3.6.1 (lines 786-795); §3.7.1 (lines 838-848)): Integrated execution preserves baseline/data/measurements, preregistered success/falsification boundaries/classification, frozen dependencies and capsule permissions. Builder declares without installing/discovering/mutating dependencies; Stage 3.7 provisions the unchanged set. Construction, empirical measurement, scientific classification and infrastructure admission remain distinct.
- **FR-005** (§2.4, §2.9): The complete journey accepts only permitted input/evidence sources and enforces the untrusted-code boundary: no undeclared dataset acquisition, arbitrary repository cloning, host access or undeclared network/system effect.
- **FR-006** (§1.4; §2.8; §2.10; §4.3.3 (lines 1502-1521); §6.2): Assembled runs retain attributable artifacts/execution/Gate records outside compact agent memory. Audited local correlation joins model calls to Observation/run/stage/role/capsule/version; attribution-only labels are absent from provider requests. Mandatory Tier-1 failure prevents semantic review; reviewer remains read-only.
- **FR-007** (§2.7; §4.6.4 (lines 1818-1826); §6.2; §6.4 (lines 2299-2333); §6.8): Blocking faults halt and retain evidence. Interactive mode supports human inspection/abort/correction/explicit restart; explicit headless evaluation follows AC-012 without prompts. Neither mode permits autonomous repair, hidden retries, automatic resume or weaker Gate policy.
- **FR-008** (§2.3, §6.3, §6.10): The complete local single-user candidate can be installed, configured, started, observed and inspected through required supported workstation surfaces, with report retrieval and source-required local security.
- **FR-009** (§1.3 (lines 75-125); §1.5 (lines 174-192); §2.11 (lines 389-414); §4.4 (lines 1540-1736); §6.11 (lines 2466-2489)): M1 includes required offline RSI Target 1: bounded rank_opportunities improvement in sandbox screening_capsule through a fixed target-independent engine/profile, preserving production behavior/interfaces and referee. Hidden sets remain inaccessible except bounded aggregate evaluation; every mandatory intentionally violating case is blocked with attributable evidence; violations halt the RSI session and autonomous continuation requires explicit human clearance, scores/audit reconcile, vulnerabilities/residual risks are documented, and human admission/activation/rollback governs adoption. Target 2 text mutation is conditional on bounded headless model execution and otherwise defers without blocking M1.
- **FR-010** (§1.3 (lines 75-125); §2.1; §2.2; §2.12; §6.1; §6.12 (lines 2490-2508)): M1 acceptance covers required static research/workstation/evaluation support and offline RSI Target 1. Dynamic/model/alternate-Verifier Phase 2 experiments remain isolated, non-blocking and absent from production unless promoted through separate product/architecture revision. Approved experimental access does not alter static Codex.
- **FR-011** (§1.6, §6.13): The integrated candidate and acceptance claims trace to the registered PRD and architecture decisions; architecture refinements do not silently alter product behavior, scope or acceptance.

- **FR-012** (§4.5.2 (lines 1748-1757); §4.6.4 (lines 1818-1826); §5.3.1 (lines 2089-2098); §5.6.5 (lines 2228-2248); §6.4 (lines 2299-2333)): Assembled explicit headless evaluation accepts input/configuration/seed where supported, executes without prompts and returns stable machine completion with run_id/Run Bundle reference. Injected blocking failure is durably recorded, returns non-zero and never releases downstream. Bundle records actual frozen capsule/library/routing/evaluation/RSI state and requested/effective seed; unsupported deterministic endpoint control is disclosed.

- **FR-013** (§5.6.5 (lines 2228-2248); §1.3 (lines 75-125)): Pre-declared approved ablations are labeled development/evaluation, preserve actual executed configuration and cannot silently alter active runs. Removing/replacing mandatory controls prevents valid Phase 1/Definition-of-Done acceptance and cannot automatically change production standing/activation.

### Key Entities

One identified integrated candidate, complete source/AC allocation, valid child block/boundary evidence, permitted research inputs and fixed execution/evaluation settings. Attributable whole-system verification results and retained run evidence; this is a normal verification TASK, not an additional runtime API. References to child agreements do not duplicate their authority.
