# Heterogeneous execution integration recipe

This capsule runs CPU references, not a live model, CUDA pipeline, or asynchronous job service. Native tools execute synchronously through the existing CCv2 job host. Every tool takes one inline `request` JSON object; fixtures enumerate the concrete fields. `plan` uses per-expert measured CPU/GPU milliseconds and transfer bytes/bandwidth, preserving a six-ID selection from 384 experts at one of 40 layers. It compares CPU compute plus roundtrip activation transport against GPU compute plus absent-weight transport. Ordered greedy placement is capacity constrained and is not a global makespan optimizer. Repeat calibration for decode and each prefill batch/shape rather than scaling decode timings linearly.

On GB10 ARM64, CPU/GPU physical RAM is shared: reserved+CPU allocations+GPU allocations+scratch+new replicas must fit one `physical_capacity_bytes`. GPU/CPU capacities are not additive. Explicit replicas consume real extra bytes; aliased allocations must already be de-duplicated in supplied residency accounting. A zero-copy mapping still needs measured synchronization/page migration/visibility cost; substitute measured effective bandwidth/cost, never assume PCIe or free transfers. Decisions use end-to-end synchronized samples with identical tensor shape, dtype, threads, and residency; no fixture cost is a hardware result.

`execute_reference` implements selected expert matrix-vector products and weighted reduction in router order. It deliberately represents the expert projection/reduction hook, not an entire gated MLP. It executes all selected IDs and retains coefficients; there is no expert dropping, replacement, renormalization, or speculative acceptance. Its `stdlib_cpu` result establishes a portable numerical oracle, not actual heterogeneous dispatch.

For a native engine implement the seam after router top-k and before the expert matmul: capture layer/token IDs, six expert IDs, original coefficients, and tensor shape/dtype. Bind a measured plan to that exact set and device generation. At the selected expert compute hook dispatch the same tensors to supported CPU or GPU implementations; at weighted reduction restore router order. Readiness requires per-expert buffer version and completed producer event before consumer launch, plus a retained ownership reference until the final consumer event. Cancellation joins outstanding producers before freeing buffers. Capture actual kernel/backend invocation counters and compare all expert outputs and final model outputs to the baseline. No production symbol name is assumed across upstream revisions; locate and pin the actual router, expert `mul_mat_id`, and backend scheduler seams before patching.

`overlap_schedule` simulates a transfer engine and serial compute stream with explicit ready times. Its optimistic schedule assumes unlimited staging lifetimes, independent engines and no shared bandwidth contention. It is a lower-bound candidate estimate, not proof that double buffering can realize it. A native two-buffer implementation must add buffer-release dependencies and reject overwrite before consumer completion. Test starvation, long transfers, empty/invalid lists, cancellation, and peak allocation before claiming overlap. Batch versus decode estimates take separate measured stage inputs and report total time per supplied token count; they do not claim batch-independent expert work.

Read SOURCES.json for pinned primary repositories. KTransformers/Fiddler motivate moving activations to CPU experts; FlexGen/ZeRO-Inference motivate throughput-oriented offload/overlap; Strata motivates measurement-driven placement. Their discrete-device bandwidth assumptions do not directly transfer to unified GB10. LiteMoE is ambiguous; PowerInfer activation sparsity and PowerInfer-2 mobile algorithms require model/hardware validation. AirLLM layer streaming is a separate granularity. Quantized kernels belong to the precision capsule's approximate gate.

Acceptance before engine promotion: preserve router IDs and coefficients; per-shape CPU/GPU reference agreement within the unchanged baseline's explicit arithmetic tolerance; exact greedy output where the task requires it; correct event/lifetime traces; shared-capacity peak measurement; ARM64 kernel build and hardware runs; repeated untraced baseline/candidate timing on the fixed workload. This capsule supplies no factory qualification certificates or performance claims.
