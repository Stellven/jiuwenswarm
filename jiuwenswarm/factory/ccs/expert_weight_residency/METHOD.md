# Expert Weight Residency Builder 1.0.0

`plan(inputs)` accepts the fixture schema. Byte counts are bounded nonnegative integers; physical/fallback/I/O capacities are positive. Repeated allocation IDs with identical kind/bytes are charged once; conflicts fail. Contexts are alternative admitted configurations, NOT concurrent sequences: startup reserves their maximum sequence-state amount. Concurrent sequence bytes must already be aggregated by the host in each reservation. Infeasible plans never authorize execution. The 96 GiB illustration yields 24/16 GiB context capacities and a fixed 16 GiB startup slot pool; these are illustrative, not measured.

Inventory and training rows use (checkpoint manifest SHA256, layer, expert, packed layout including tensor role). Training/evaluation request sets must be disjoint. Freeze frequency-per-byte priority before evaluation; ignore all nontraining trace rows. Return original tensor/expert warm keys, environment and canonical receipt digest. This is demand-warmed static protection, not eager preloading. Idle unprotected slots use LRU. The fallback reservation prevents warm protection consuming the entire byte pool; allocation and I/O pressure may explicitly bypass to the original mapping.

`residency_header` is the portable native slot interface. Capacity covers owned packed bytes; I/O writes into those same allocations, so it is not charged twice. Active leases, reserved bytes and outstanding read bytes are separately counted. Same-key waiters pin the generation before waiting. Read completion publishes ready bytes; all readers must release before eviction. Cancellation wakes waiters and suppresses publication, but synchronous pread must finish before drain. Never destroy the cache while readers/fills remain. The CPU fixture tests eviction under an active reader, generations, singleflight, failed fill, cancellation and protected warm entries.

This is not a physical RSS guarantee: original mappings, page cache, allocator overhead and backend memory need host admission and headroom. No GPU allocation, timing or DeepSeek correctness claim is made.
