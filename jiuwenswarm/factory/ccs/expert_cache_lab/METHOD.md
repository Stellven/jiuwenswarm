# Expert cache and causal prediction reference

`validate`, `replay`, `predict` accept `inputs.trace`, an ordered event list with integer `seq`, nonempty `request`, integer `token`, `layer`, `expert`, positive `bytes`. Default geometry is 40 layers and 384 experts; override `layers`/`experts`. Six activated experts per layer can be represented as six events; no fixed activation count is asserted or silently synthesized. Keys are `(layer,expert)` and are shared across requests; request token order must be monotonic. Expert byte sizes cannot change. No input paths are accepted.

`replay` adds `capacity_bytes` and `policy` (`lru`, `lfu`, `hybrid`). Oversize experts stream on demand without admission. LFU counts historical demand, including misses. Hybrid evicts the smallest `(frequency+1)/bytes` score with deterministic recency ties. This is an original illustrative policy, not MoE-Infinity's production policy. Variable byte capacity and layer keys are real constraints. Neither admission nor eviction changes routing.

`predict` forecasts an **atomic request/token/layer selected-expert set before observing any expert in that group**. All events belonging to a group must be contiguous; duplicate experts and split train boundaries inside groups are rejected. Default `top_k` is six, independent of current labels. `train_events` selects a chronological training prefix on a group boundary; holdout groups are predicted then observed for future groups. Layer-scoped set transitions use per-request previous sets; there are no intra-group prediction updates or cross-request transitions. Metrics count selected-set overlap, not arbitrary serialization order.

Optional `evaluation_requests` selects a strict request-separated frozen holdout instead of `train_events`: other requests train the model, evaluation labels never update transition/frequency tables. Previous observed sets still supply causal context for subsequent tokens of an evaluation request. This is a request-corpus split, not a chronological split across all requests. Source request corpus may contain timestamps later than evaluation requests; use chronological mode for temporal deployment estimates. Predictions alone do not prove next-token runtime readiness, useful prefetch lead time, cache engagement or speedup.

Run `python verification.py`; the separate factory test file exercises all capabilities through real Host.prepare/call and additional invariants. No GPU execution, upstream runtime reproduction, factory qualification admission, or measured speedup is implied. Caller must account for model/dense weights, KV and scratch outside this expert-only budget; GB10 unified memory makes a CPU/GPU cache-copy model hardware dependent.
