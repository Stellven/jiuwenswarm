# Report to proposed next input

Use `followup` after a completed or failed experiment report. Read the report and original task contract, select one unresolved question, and cite the episode evidence. The output proposes an objective, ontology slice, hypothesis, expected evidence, bounded experiment and capsule candidate. It is not an admitted task or changed contract.

Treat basic goals such as “make decode faster” as a reason to inspect multiple possible causes, not permission to change everything. Prefer the earliest missing prerequisite: recoverable evidence, correctness, repeatability, then bottleneck observation, then one-variable treatment.

The JiuwenSwarm agent decides what to do under its current contract. If the next input changes a scored workload, correctness rule or acceptance policy, prepare a new revision for operator admission/freeze. Do not inherit grants or source permissions from a report. Do not automatically activate a discovered method or component.

Keep failed/null ideas and resource costs in subsequent cycles. A generated candidate needs applicability, source mapping, bounded effects, positive and negative replay cases, correctness and observer checks, rollback and separate promotion authority. Missing measurements may prioritize inspection; they do not predict performance benefit.

To test a second cycle: preserve the first report, publish the proposal separately, admit any necessary task revision explicitly, run the next bounded action, retain its report, and analyze both reports. Verify that new evidence changes the unresolved question while the original contract and failure history remain intact.
