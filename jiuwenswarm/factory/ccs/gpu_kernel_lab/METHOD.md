# Shape-specific expert launch batching

Input schema is a flat row-major FP32 `weights[experts,rows,cols]`, `inputs[tokens,cols]`, `routes[tokens,top_k]` and original finite `gates[tokens,top_k]`; dimensions, indices, magnitudes and work are bounded. No route is dropped, renormalized or padded. Duplicate expert selections remain legal. `evaluate` computes the full weighted expert linear output with Python float64 math.fsum. This is the linear subproblem, not the nonlinear gated FFN or a whole MoE layer.

`benchmark` sends those exact tensors to the fixed bundled native_experts binary. The native FP64 CPU oracle uses the actual FP32-rounded input. Baseline dispatches one identical row GEMV kernel per route plus a deterministic combine kernel; candidate dispatches one grid over all routes plus the same combine kernel. Each CTA reduces the input dimension with shared-memory FP32 pairwise reduction, preserving expert IDs and gate coefficients. Sweep threads 32/64/128/256, five warmups then repeats 5..1000. CUDA events time kernels in the default stream. Transfers, parsing, allocation, Python CPU oracle and startup are excluded. Every variant must pass absolute tolerance `2e-5 + 2e-5 * max_abs_reference`; returned best configuration is launched again and compared independently to Python FP64. This allows FP32 reduction rounding and is not an exact-output claim.

Build in this directory: `/usr/local/cuda/bin/nvcc -O3 -std=c++17 -arch=sm_121 native_experts.cu -o native_experts`. Existing CUDA13 toolkit only; no install. GB10 SM121 target is deliberate. The runnable binary is host/toolkit-specific; rebuild from source elsewhere. The payload byte count includes FP32 weights, activations, gates, intermediate/output and int32 routes. It excludes CUDA context, allocator metadata, host duplicate storage, and driver accounting. Shared memory per CTA is `4*threads` bytes. No PCIe memory-sum assumption is appropriate on GB10 unified memory.

This first round tests launch aggregation and reduction shape. It does not implement tensor cores, weight reuse across tokens, grouped GEMM, MegaBlocks or ScatterMoE. A win on small synthetic shapes can vanish when experts are wide or token batches large. Report all candidate times and losers. Alternate/randomize variants and use repeated independent processes before trusting close results. One fixed-order component sweep is screening evidence only. For an engine follow-up, capture real `(tokens,top_k,rows,cols)` distributions, integrate at the expert linear hook, check native model outputs and then measure prompt/decode phases separately. No model tokens/s is inferred from this benchmark.

First manual round on NVIDIA GB10 SM121, 2026-11-15: serial-route/best-batched latency was 29.104/5.124 us (small), 18.509/6.156 us (single-token decode-shaped), 265.301/12.196 us (16-token prefill-shaped), and 26.182/6.073 us (127-column tail). All 16 batched configurations and four baselines met the FP64 oracle gate; worst Python-reference error was 7.16e-8. CTA64 selected all shapes, but several microsecond candidates were effectively tied; this single ordered sweep does not establish a universal optimum. The prefill-shaped result removes 65 launches down to two, explaining the large component ratio without proving an engine benefit. Wider CTA256 in that case took 22.550 us versus CTA64 12.196 us, retaining a losing shape choice. Full timings, exact payload counts, seed-free input recipe/hashes and source/binary hashes are in ROUND1.json. Reproduce in an exclusive slot with `python3 measure_round.py --exclusive-gpu-slot`.

Portable and authority boundaries: the default CC bundle ships Python and native source with JSON evidence; measured ARM64 binaries are retained separately under runtime-native-artifacts-20261115. Native invocation never compiles and fails clearly if the binary is missing, the host is not Linux ARM64, or its ELF machine differs. Source portability to other CUDA devices is unqualified. CPU `evaluate` and `verification.py` remain portable and require no GPU. Native reproduction needs an explicit authorized build first, never a hidden dependency install.

The `benchmark` CC now declares `changes: [process.exec, gpu.use]`, `needs: [python, gpu]`, and a required host-bound GPU handle. CCv2 checks session grants, capability grants and bound resources before process dispatch (ccv2.py around 640–686). A CPU mission must omit gpu.use and provide no GPU handle, so invocation is denied before native launch. A JSON request field cannot grant GPU authority. The example handle is a placeholder the host must bind; direct fixture invocation fails without packet resources. GPU handles are issued only after the operator/host reserves an exclusive slot. This package does not acquire the factory job queue automatically: do not issue a handle during a running engine measurement. Direct Python imports and measure_round.py are trusted developer utilities, outside CCv2 authority; they must not be exposed as alternative agent tools.

Selection limits: the first retained round actually used **100 timed repeats per variant**, after five warmups; EXAMPLES.json separately uses 50 as a small invocation example. ROUND1.json records the actual 100. Choosing the minimum of four candidates introduces selection optimism. Fixed serial-first and CTA32/64/128/256 order allows clock/thermal/cache effects to confound comparisons, and the timed repeat batch is not 100 independent process samples. These are screening observations. A second round should select configuration from one set, then compare fixed candidates in alternating/randomized order on held-out repetitions/processes and report medians/spread. Close CTA choices remain unresolved. Event timings omit transfers/launch setup/startup, and serial event intervals can include device idle gaps while the CPU enqueues the route kernels. The large ratios primarily diagnose dispatch aggregation in this deliberately serial baseline.

The wrapper validates native replies before marking correctness: exact output
length, finite numeric output values, boolean native correctness gate, four
finite positive candidate timings, finite positive baseline/best timings and
speedup, and finite nonnegative native error. Nonfinite JSON numbers are rejected
throughout the reply. The independent Python comparison does not truncate a
short or overlong native output. Malformed-reply tests stub native transport and
require no GPU or compiled binary.

## Verify dispatch before proposing an engine change

Read the parent image/build/load receipts, map the actual decode tensor shapes to the backend dispatch, and qualify any proposed batching against the pinned library. Count routed matvec launches separately from activation quantization, expert transfers and gate post-operations. When the existing backend already batches every eligible route, stop before patching or assembling an image.

In this run, the read-only `trace_dispatch` capability binds AQBC's executable and CUDA library to its committed/frozen source, examines the headers of all 11 GGUF shards, and follows the recorded single-slot CUDA MoE cache path. The pinned source implements one-token MMVQ for 4096-by-4096 IQ2_XXS gate/up and Q2_K down. Eight route IDs remain the launch grid's eight Y channels even when the synthetic bank is smaller than the real 4,625-slot view. The slot IDs address weight slices, with identical row and slot strides in the fixture. Few-row MMQ starts at two tokens for these types on GB10.

The pre-graph no-model fixture source is `fixtures/muse_dispatch.cpp`. It links to GGML CUDA and base libraries copied from a stopped AQBC image container, byte-matched to the retained R8 build. A one-token projection uses synthetic quantized zero weights, explicit permuted slot IDs and exact activation layout. Separate gate/up and adjacent fusion-eligible gate/up are checked independently. The zero-output check is a fixture guard. The evidence qualifies dispatch, without claiming numerical parity on model weights or measuring Muse speed.

Reproduction on the approved GB10 fixture slot:

1. Copy the AQBC `/opt/llamacpp` libraries using a scratch stopped Docker container. Compare their hashes to the image receipt and pinned build files. Provide the pinned `ggml/include` headers from the frozen engine source and the installed CUDA include directory.
2. Compile only `fixtures/muse_dispatch.cpp` with `g++ -std=c++17 -O2`. Link `libggml-cuda.so.1`, `libggml-base.so.1`, `libggml.so.1` and `libcudart.so.13` from the matching image/build package. Set `LD_LIBRARY_PATH` to resolve those libraries and their pinned runtime dependencies.
3. Check the GPU compute inventory. Run the fixture executable separately with arguments `iq2_projection`, `q2_down`, `iq2_gate_up_pair` and `iq2_adjacent_gate_up`, leaving CUDA graphs enabled. Capture each process with `nsys profile --trace=cuda --cuda-graph-trace=node --sample=none --cpuctxsw=none --capture-range=cudaProfilerApi --capture-range-end=stop --export=sqlite --output=<new-case-path>`. Keep stdout, the Nsight report, the SQLite export, and the source/executable hashes.
4. The native CPU-only verifier checks the retained evidence digests and independently queries `CUPTI_ACTIVITY_KIND_KERNEL` via `StringIds` for kernel names, order, geometry and graph node IDs. It compares its rederivation to the raw trace and seals the result. A collector JSON field cannot approve a build.
