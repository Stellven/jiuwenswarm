为什么任务规划需要引入 TLA+ / TLC？（而不是只用 JSON + 静态检查）

用 TLA+ 状态机在规划阶段穷举验证并发与边界，对外依然输出标准 JSON，下游零额外依赖。

一、本质对比：TLA+ 语言 vs JSON 语言
JSON：静态数据结构（只看“纸面图纸”）
只擅长描述“有什么节点、连了什么线、配了什么字段”，没有时间推进、状态变迁、并发交错和资源抢占的语义。
  • 基于 JSON 写静态规则只能做“查漏补缺”；
  • 永远抓不住跑起来之后的动态死锁与并发撞车。
TLA+：形式化状态机与时序逻辑语言（“发车前全演练”）
原生描述“节点状态如何流转（等待/执行/完成/失败）、谁在何时抢哪把锁、重试额度还剩多少”。配合 TLC 检验器提前演练所有并发交错与失败路径，抓出三类静态必漏的真问题：
  • 并行抢锁撞车 · 重试额度归零饿死 · 跨分支互等死锁
工程闭环（内部把关，外部无感）：验证不过时，系统把反例翻译成一句人话让 AI 自动修对；验证通过后，对外仍转回标准 JSON 交付，下游调度器无需安装 Java 或懂 TLA+。
二、公平实测对比报告（对比传统静态基线方案）

测试口径：基于真实推理引擎优化任务（llama.cpp + DeepSeek-V2 / Muse-816B），共 19 个场景（6 个正常流程 + 10 个静态检查全放行的隐蔽故障 + 3 个自动修复闭环）；两组使用完全相同的输入与同一套 100 次并发调度模拟器（相同随机种子、15% 瞬时失败率）。

基线定义：“传统静态规划与校验方案”指原版单次尝试规划器 + 纯静态规则校验器，仅在 JSON 层面核对字段完整性、基础依赖无环、端口类型与静态权限，规定每步只允许执行 1 次、不建模并发锁与重试演化。

核心对比指标 基线方案：传统静态规划与校验（单次尝试 + 纯静态） 本文方案：TLC 内部形式化验证（输出标准 JSON）
正常流程交付率 (6 例) 70.83% （每步限跑 1 次，遇瞬时失败即挂） 100%（0% 误报，平均耗时 1.32s）
隐蔽故障拦截率 (10 例) 0%（10/10 全部放行） 100%（10/10 拦截，平均耗时 0.42s）
上线后平均浪费 (失败前白跑) 白跑 4.38 节点 / 107.3 轮 下游浪费 0
反例自动修复 (3 例) 不支持自动修复 3/3（100%，反例引导下一轮自动修对）

一句话结论：在保留既有静态校验基线的基础上，仅增加不到 1.4 秒的内部 TLA+/TLC 形式化验算，即可将隐蔽运行期故障逃逸率从 100% 降到 0%，同时对外保持 100% 标准 JSON 交付。
