Experimental Setup: What Are the Inputs, Baselines & Fairness Rules?

Written for colleagues and reviewers outside this subsystem: what goes into the planner, what the three compared pipelines actually do, and why every metric below is apples-to-apples.

1. What Goes In (Real Engine Tasks, Not Toy Graphs)

  • Single Task Specification (TaskInput): Names the target inference engine and locked git commit (llama.cpp), model architecture/quantization format (DeepSeek-V2 / Muse-816B-NVFP4), single-machine hardware target (DGX Spark GB10, sm_121, 128 GB unified memory), structured acceptance criteria, and allowed system permissions.
  • 6 Healthy Production Pipelines: Single-feature optimization patch, 3-to-4-module concurrent integration with conflict-grouped merges, and mixed converter + scale-wiring + weight-packing flows.
  • 10 Static-Bypass Defects (4 Failure Modes): Parallel code edits or builders without exclusive locks (3), valid settings assigning build_attempts = 0 so builds starve (2), scheduling-order loops causing deadlocks (3), and packaging/delivery steps wrongly given workspace write rights (2).
  • 3 Self-Repair Loops & 4 Scaling Tiers (k=2..5): Round 1 faults repaired from TLC counterexamples in Round 2, plus parallel fan-out scaling benchmarks.

2. Three Comparison Baselines (vs Old M1)

  • Baseline 1 — Old M1 (M1 Planner + M1 Verifier): Flat legacy plan layout without autonomous multi-step decomposition or conflict clustering, hard-locked by original M1 policy to 1 attempt per step (no retries on transient failures), and checked strictly by the original M1 static verifier (research/binding.py:plan_checks).
  • Baseline 2 — M2 Static-Only (Bridged M1 + M2 8-Rule Static): Uses the autonomous step + CC Library planner (with retries and merge clustering) plus bridged M1 checks and M2’s 8 semantic rules, stopping at static inspection without TLC.
  • Treatment — TLC-Verified Planner (M1+M2 Static + 2-Pass TLC → JSON): Runs identical compilation and static checks as Baseline 2, then verifies load-time invariants (ASSUME) and 2-pass TLC state-space exploration internally before emitting standard runnable JSON deliverables.

3. Why This Comparison Is Fair (Fairness Contract)

  • Identical Inputs & Compiled Plans: All 3 arms evaluate the exact same 19 task scenarios, capsule catalog, and compiled node structures (only M1’s single-attempt cap distinguishes Baseline 1 runtime retries).
  • Identical Scheduler Simulator: Every admitted plan executes inside the exact same deterministic Monte Carlo scheduler simulator (100 trials/case, fixed seed = 42, 15% transient step-check failure retry rate, and identical exclusive lock & permission rules).
  • Zero Downstream Burden: Internal TLC checks block bad graphs upfront without requiring downstream execution code to run Java or TLA+—all delivered artifacts are standard JSON.

      8. Methodology Rigor, Threats to Validity & Follow-Up Q&A

      Q1: Why bridge legacy M1 binding.plan_checks instead of deleting it, and why aren’t M1 + M2 static checks enough without TLC?
      Bridging M1 preserves all 10+ proven M1 invariants (coverage, port compatibility, dependency closure, predecessor acyclicity) without silent regression via m1_verifier_bridge.py. However, real execution proves M1 alone suffers on Class A reliability because binding.py:98,453 locks max_attempts_per_node == 1, and BOTH M1 Legacy and M2 Static let 100% of Class B concurrency, starvation, depends_on deadlock, and build/deliver write-privilege defects bypass static checks. Separating load-time ASSUME least-privilege assertions and TLC temporal state exploration catches 100% of them.
      Q2: How does internal TLC model checking pair with standard JSON deliverables?
      ai_planner renders and runs 2-pass tlc2.TLC (plus load-time ASSUME invariants) internally during each planning round inside rounds/<r>/tla/. Only once proven does _accept() emit verified standard JSON (contract.json, plan.json, graph.json, verification.json, task.json) for planner.py and scheduler.py without exposing .tla as an external dependency — while tla_graph.parse_taskgraph_tla() also validates ms pure-Python parity.
      Q3: What is the boundary between formal graph.tla verification and capability semantic checks / blind code review?
      graph.tla + TLC proves orchestration-level safety and liveness (DependencyOrder, ExclusiveResources, ParallelBound, AttemptBound, NoStuck, HaltsDelivered, and least-privilege workspace invariants). Functional C++/CUDA kernel correctness, checkpoint quantization parity, and code quality remain enforced per node at execution time by dual verifiers (capsule .verify/.verify_pack/.verify_recipe plus independent blind code review in node_check.py) bound inside NodeSpec.
      Q4: How does TLC scale when parallel builder branches grow, and what are the main threats to validity?
