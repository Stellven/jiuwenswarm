T28 is an offline, plan-only benchmark of declared versus undeclared capabilities. No research plan is built, bound, frozen, admitted, or run. Authoring and tests make no model calls, HTTP requests, Docker calls, or credential reads.

Run through `scripts/ai4r-bench` (see "Origin" above). The delivered tests make no model calls, HTTP requests, Docker calls or credential reads; only `run --execute` calls the model.

`plan` prints 24 prompt SHA-256 hashes`plan` prints 24 prompt SHA-256 hashes, UTF-8 byte lengths and character counts, with no subprocess. `run` refuses to call Codex without `--execute`. Each task/condition/repeat invokes exactly one `codex exec --skip-git-repo-check -m MODEL -s read-only --ephemeral -C EMPTY_DIRECTORY -o REPLY -` with prompt stdin, a 300-second timeout and no retries. The installed executable's absolute path replaces `codex`. Timeout cleanup terminates the Windows process tree. `library.py` captures exact release declarations and checking assets with the product factories in memory: seven scientific stages, two integrated paper capsules and nine current extension manifests (18 selectable capsules). Manifest/hash validation remains enabled. The full snapshot also includes four installed nonselectable core compiler/planner/verifier entries (22 entries total), captured with the product prepare-only factory. Historical releases, compiler, planner and verifier are not selectable. This is a controlled installed-release projection, not a claim that optional extensions are admitted or active in a running deployment. No live app state is inspected. The projection assumes admission of these installed releases with 16384 MiB worker/verifier ceilings. Snapshot budgets follow `LibraryService.snapshot`: worker wall time plus one bounded review per output; audited worker model invocations plus one review per output; maximum worker/reviewer memory. The release catalog and every declaration/snapshot are schema-validated, and `verify_catalog` checks complete exact membership and ports.

`tasks.json` holds 12 schema-valid Brief v3 tasks with the exact same serialized task text in A and B: five feasible, three missing capabilities, two mandatory reservations above policy aggregate ceilings, two missing inputs. `plan_integrity.py` independently checks normalized nodes against frozen ground truth. It does not call product `plan_checks` to determine independent defects. It checks input/output existence, duplicates and requiredness, exact future artifact types/schema refs, external availability, conditional host producer requirements, explicit dependency closure/cycles, known capability/check identities, coverage, acceptance anchors, effects/authority and limits. JSON node array order is immaterial; explicit dependencies define topological order. Task capability requirements accept the installed `_typed` operation variants. Coverage is explicit via A tags/maps or B `covers`; labels require the intended work as well as obligation IDs. Defects count individual failed invariants, so an unbound port and an unused mandatory task input can be separate defects. Malformed JSON is an `uncovered_obligation` failure with `parse_error`, never silently dropped. All 13 requested defect classes are reported, including zero counts.

The independent budget metric sums all node reservations, including memory, per this benchmark request. The product sums time/calls but takes maximum node memory. Its different judgment is retained beside A's independent score as `product_gate_failures`. That diagnostic calls the real `jiuwenswarm.research.binding.plan_checks` with `plan_source='planned'` and the exact expected input refs, without Binder, a worker, a gate decision, or execution. A correct INFEASIBLE reply has no candidate graph to pass to that function; schema/parsing errors are reported as failures.

`score` writes `scores/<model>.json` and a Markdown table with condition-level validity, per-class defects per reply, infeasible-handling accuracy, acceptance-criterion machine-checkable fraction and repeat stability. Validity means zero independent defects, including correct bounded rejections. Infeasible accuracy is the fraction of the seven non-feasible tasks correctly rejected with a reason naming the missing capability/input or budget. The JSON also includes overall feasibility-decision accuracy. The acceptance fraction is anchored criteria divided by all supplied criteria; absent criteria produce their own defect rather than an invented denominator. Stability is mean per-task modal capability-set frequency across repeats; malformed replies do not earn stable empty-set credit. Single-repeat stability and empty denominators are null, never fabricated zeroes or perfect scores.

Limitations: information asymmetry is the point. A receives substantially more tokens, policy detail, host binding instructions and a richer output schema, so this does not isolate typed ports alone or measure a token-matched effect. B's skill names/summaries can naturally reveal hints. Brief inputs describe types independently of the library framing. Feasibility and work coverage are manually authored labels; equivalent unexpected workflows may need human adjudication. Acceptance machine-checkability is a lexical named-output/check-anchor proxy, not a proof that the criterion is executable or scientifically sufficient. Reason matching for INFEASIBLE is a bounded keyword heuristic. Structural/type integrity is not semantic correctness. The checker does not emulate the complete Binder, qualified intake, semantic verifier or execution environment. This small task sample emphasizes generic and supporting workflows; it does not estimate complete scientific POC planning performance. Plan quality is not execution success.
